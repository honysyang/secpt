# 挖洞能力与交付 · 提升路线图（攻击者优先）

> 视角声明：本路线只回答一个问题——**"这个阶段让我们能多发现什么洞、多证明什么洞、
> 多交付什么价值？"** 防御/审批/通知/产品层全部后置（用户明确"暂时不考虑防"）。
> 参考来源：ARTEX 对标（docs 见会话记录）、HPTSA/VulnBot/CHECKMATE 架构研究、
> secpt 真实靶场运行经验。每阶段给出可验证的验收指标。

---

## 0. 能力模型：挖洞系统 = 五个面

```
观察面（能看到什么）      → 资产/源码/流量/API 面
记忆面（观察→假设）       → 关系与血缘，交叉点出洞
验证面（假设→证据）       → 可复现，确认分级，对抗式复测
规划面（时间分配）        → 深度优先，否定记账，覆盖度
交付面（证据→价值）       → findings 生命周期，CWE 分类，报告与 PoC 包
```

secpt 现状评分（攻击者视角，5 分制）：

| 面 | 现状 | 短板 |
|---|---|---|
| 观察 | 3 | 有 recon/web 工具，无流量层，无 API 面方法论 |
| 记忆 | 2 | warroom 平表，无血缘；GraphStore 半退役；经验闭环已有 ✓ |
| 验证 | 1 | findings 是正则扫的字符串，无确认语义，无证据链 |
| 规划 | 3 | 单链高效但靠模型自觉；stages 有交接无意图/frontier |
| 交付 | 1 | 只有 report.md 空壳，无 findings 生命周期，无分类法 |

**杠杆排序结论：验证(1→4) 和 交付(1→4) 最便宜最急；记忆(2→4) 最贵但决定 0day 上限。**

## Phase B1：Findings 证据链与确认分级（验证纪律）

**黑客逻辑**：CTF 的答案是点状的，0day 的产出是**可复现的证据链**。现在系统的
finding 只是 `credential:xxx` 字符串——既不能交付，也不能区分"疑似"与"已证实"。
没有确认分级，挖得越多噪音越大，最终淹没真洞。

**做什么**：

1. **Finding 数据模型升级**（`src/secpt/findings/`，新建）
   ```python
   Finding {
     id, title, vuln_class, severity(critical/high/medium/low),
     status: inferred | confirmed | false_positive | duplicate,
     evidence_refs: [traffic_id | file_path | step_ref],   # 证据指针，非内联文本
     reproduction: str,          # 最小复现步骤
     first_seen: {job_id, step}, # 血缘起点
     reproduced_by: [retest_id], # 对抗式复现记录
   }
   ```
   存储：SQLite `findings` 表升级（现 store.py 已有雏形）+ `var/findings/` 详情目录。
2. **确认纪律进 prompt**（数据驱动）：`hunter.yaml` profile 的 stop_condition 明文——
   "只有本次运行真实触发并拿到响应证据才可 report confirmed；否则记 inferred"
3. **对抗式自检**（复用 evaluation 基建）：`LLMJudge` 加一个 verify 模式——
   用与首次不同的参数/路径独立复现一次，两路证据一致才升级 confirmed。
   （证伪和证实同等有价值。）
4. **Retest 闭环**：`secpt retest <finding_id>`——取 reproduction 最小化重放，
   结论 reproduced / fixed / inconclusive 三档。

**验收**：人为埋一个假阳性（只改版本号不真触发）→ 系统必须标 inferred 而非 confirmed；
真洞 → retest 能独立复现。findings 表可查 `secpt findings --status confirmed`。

## Phase B3：流量证据层（取证基础设施）

**黑客逻辑**：**挖洞工作的 50% 是取证**。不能复现的请求等于没发生过。
交付物被质疑时，唯一硬通货是原始报文。secpt 现在连请求/响应都没存全
（工具输出截断 8000 字符就丢了）。

**做什么**：

1. **透明 MITM 录制**（`src/secpt/traffic/`，新建）
   - 内嵌 **mitmproxy**（Python 原生，比 ARTEX 的 go-mitmproxy 集成更顺）
   - Bash 工具自动注入 `HTTP(S)_PROXY` + 分生态 CA 变量（`SSL_CERT_FILE` /
     `REQUESTS_CA_BUNDLE` / `NODE_EXTRA_CA_CERTS` / `NODE_EXTRA_CA_CERTS`…）
   - worker 的 curl 命令**零改造**被录制；WebFetch 类工具走代理并**正常校验**
     代理 CA（绝不 `verify=False`——那会丢掉 TLS 层信息且养成坏习惯）
2. **内容寻址快照**（`src/secpt/evidence/`，新建）
   - 原始 request/response 按 SHA-256 存 `var/evidence/blobs/<前2位>/<hash>.bin`
   - 与可清理的热流量分离；多 finding 共享同一 blob
   - 索引：SQLite FTS5 全文检索（URL/头/体）
3. **证据绑定**：finding ↔ 流量快照，角色四档：
   `baseline / proof / verification / supporting`
   - 绑定写进 Finding.evidence_refs；`secpt findings show <id>` 直接吐
     request.http / response.http 文件

**验收**：任意一次 solve 运行，能导出 `secpt evidence export <job_id>` 拿到完整
HTTP 会话原始报文；finding 详情附带可重放的 proof 报文。

**与 B1 的关系**：B3 是 B1 evidence_refs 的落地载体——先建 B1 的指针语义，B3 填实体。

## Phase C1：Findings 生命周期 + 报告交付

**黑客逻辑**：洞的价值 = 严重度 × 可信度 × 可消费性。挖出的洞躺在 SQLite 里
等于没挖——报告是洞价值的放大器，也是"交付"这个词的本体。

**做什么**：

1. **9 态分诊状态机**（ARTEX 同款，数据驱动放 profile/yaml）：
   `pending → in_progress → confirmed → resolved/fixed`
   旁路：`false_positive / duplicate / ignored / risk_accepted`
2. **CWE/CVE 映射**：judge LLM 分类 → CWE 编号 + 名称（带校验：编号必须存在于
   内置 CWE 字典，防幻觉）；已知漏洞比对 CVE 候选列"可能相关"（不抢 0day 的功）
3. **报告生成**（复活 `src/secpt/report/`，引入 jinja2——本路线唯一新依赖，值得）：
   - 任务级报告：目标 / 摘要 / 按严重度排序的 findings / 每个 finding 的
     描述-影响-复现步骤-PoC-证据包链接
   - 证据包：md-zip（manifest.json + 每 finding 的 request/response.http + bin）
   - `secpt report <job_id> [--format md|md-zip|json]`
4. **报告-证据一致性不变量**：证据版本号乐观并发（抄 ARTEX）——证据变了，
   报告自动标"待更新"，杜绝拿着旧证据交报告的致命错误

**验收**：对 rois 靶场跑一次 solve → `secpt report` 产出含 XSW/userType 提权
finding 的完整报告（含 CWE-347 映射、复现步骤、proof 报文），专家盲评可用。

## Phase B2：双图记忆（把 GraphStore 转正）

**黑客逻辑**：0day 出在海量观察的**交叉点**——"这个子域跑的是那个 git 泄露的源码"
"这个 403 和那个 403 是同一个 WAF 规则"。平表没有交叉点，血缘让 planner 能问
"哪些事实综合出新方向"。这是 0day 上限的决定项，也是最贵的一项，所以放在
验证和交付之后（先有证据链，记忆才有真材实料）。

**做什么**：

1. **资产图（真值库，程序算关系）**：节点 `root_domain/subdomain/ip/service/app/endpoint`，
   父子关系与去重 key 全部由代码计算，agent 只提交原始观察（复用并复活
   `core/graph/` 骨架，GraphStore 三档后端已有）
2. **探索图（血缘链）**：`goal/intent/fact/finding/hint` + 边
   `spawns/derived_from/yields/proves`；warroom 四表升级迁移
3. **锚点表**：exploration_anchors(finding_id, asset_id) → **覆盖度可计算**
   （"哪些资产已测/未测"，挖洞最怕自以为测完了）
4. **过程级 trace 检索工具**：events.jsonl 已经是 append-only 执行过程——
   加结构化检索工具（`search_traces`）让 agent 能查"我之前哪一步见过类似的响应"
   （经插件工具机制注册，零执行器）
5. **否定记账**：attempts 表现有 sha1 去重 → 加 `verdict=failed/blocked` 与
   "同目标同方法至多复核一次"策略（prompt 层 + 检索层双重约束）

**验收**：同一目标跑两个不同入口的任务 → 资产图合并去重正确；finding 可溯源到
"哪两个 fact 综合得出"；`secpt coverage <target>` 输出已测/未测资产面。

## Phase B4：规划升级 — planner/frontier（多步利用链）

**黑客逻辑**：单链靠模型自觉记住计划，摘要一压就丢。深洞（利用链 5+ 步）需要
"计划与执行分离"：planner 产意图入 frontier，确定性调度执行；模型只活在
当下的那一步，计划永不丢。CHECKMATE 的教训：长程规划交给确定性结构，LLM 只做战术。

**做什么**：

1. **intent/frontier**：`stages.py` 演进——planner（每轮新会话）产 intent
   （含完成判据、所需输入、预期输出），frontier 存 SQLite（跨 resume 持久化——
   **比 ARTEX 内存 todolist 强，天然匹配 7×24**）
2. **worker=现有单链 Engine**：领一条 intent 跑到判据满足或证伪，写回
   fact/attempt；深度优先排序（frontier 按 planner 给的优先级+深度）
3. **常驻 todolist 持久化**：利用链"记一次、逐步派"，重启不丢
4. **steer 中途纠偏**：PreToolUse hook 注入（不打断、不丢进度），复用现有 hooks 链

**验收**：需要一个 5+ 步利用链的靶场（如多层 SSO + 存储型 XSS 链）验证：
模型在 step 3 被 compaction 后仍能正确执行 step 4-5（计划不依赖上下文记忆）。

## Phase C2：0day 狩猎专项（方法论层）

**黑客逻辑**：工具齐了，打法决定产出。这一层全是数据/提示词，零新执行器。

1. **`hunter.yaml` profile**：挖洞专用（stop_condition=确认纪律、深度优先约束、
   否定记账提示）
2. **api-recon 式 skill**（`knowledge/skills/api-recon/`，仿 ARTEX 组织）：
   JS bundle harvest + 无凭据撑开 SPA 路由 + 流程门禁（禁止手写脚本不审就跑/
   grep 必须截断）+ "完成定义" Checklist——**skill 即作战手册**
3. **已知 CVE 去重**：结果比对已知 CVE 列表（防把 1day 当 0day 报，损信誉）
4. **LLM 池 failover 链**：多 provider 责任链 + 熔断 + **"零事件产出前才可切换"**
   规则（防双份输出污染执行历史）

**验收**：对一个无 hint 的真实 Web 目标跑 hunter profile → 产出 ≥1 个
confirmed finding 且带完整证据包；skill 手册可被新人/新模型直接消费。

## 依赖关系与执行顺序

```
B1 验证纪律 ──┬──→ C1 交付（findings 生命周期+报告）
              └──→ B3 流量层 ──（evidence_refs 落地）
                          │
B2 双图记忆 ──────────────┴──→ 覆盖度进报告
B4 planner/frontier ──（frontier 读双图，双图读流量证据）
C2 方法论层 ── 贯穿（hunter profile 从 B1 就能用）
```

**推荐节奏**（每个 Phase 1-2 周，各自独立可交付）：

| 顺序 | 阶段 | 理由 |
|---|---|---|
| 1 | **B1** 验证纪律 | 最便宜、杠杆最大，立刻让一切 findings 变得可信 |
| 2 | **B3** 流量证据层 | 交付的硬通货，B1 的实体载体 |
| 3 | **C1** findings 生命周期+报告 | 兑现"交付"，让系统产出专家可用的报告 |
| 4 | **B2** 双图记忆 | 挖洞上限决定项，此时已有证据链喂图 |
| 5 | **B4** planner/frontier | 深利用链，依赖 B2 的图 |
| 6 | **C2** 狩猎专项 | 方法论打磨，随用随加 |

## 明确的反目标（本路线不做）

- ❌ 审批/拦截产品化、多租户、通知渠道、Web UI（防御与运营层，后续单独立项）
- ❌ 推翻单链 Engine（CTF/短任务它是对的；frontier 只在多步利用链场景接管）
- ❌ 为具体靶场硬编码任何逻辑（所有打法进 profile/skill/prior 数据层）

## 每阶段的通用验收纪律

1. 新功能必须带单测，且 FakeLLM 无 key 可测主链路
2. `make check` 全绿才合并
3. 每个 Phase 结束在真实靶场跑一次并沉淀经验（learning 闭环的输入）
4. 设计决策写 `docs/decisions/NNN-<主题>.md`（问题→选项→取舍→实测依据）
