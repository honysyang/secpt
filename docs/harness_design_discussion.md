## 1. 六种智能体工作模式盘点

按"协调权在谁手里"排序，从最无结构到最有结构：

| # | 模式 | 怎么运转 | 渗透场景表现 |
|---|---|---|---|
| 1 | **单 Agent ReAct** | 单循环体：思考→调工具→观测→再思考。无协调者、无并行，记忆=上下文窗口 | 能跑通基础探测，但一条大输出就淹掉目标；只适合当**阶段内执行器** |
| 2 | **Planner + Executor** | planner 切任务卡，executor 逐卡跑，planner 看结果重排 | 分工清晰、可归因；但渗透是证据驱动的——新证据一出，计划快照立刻作废 |
| 3 | **Handoff 团队（Swarm）** | 多个具名 agent 互相转交**完整控制权**（SDK 内置原语） | 交接必然丢 scope 约束、风险门禁等全局事实，丢一次就是事故 |
| 4 | **Agent-as-tool** | 主 agent 保持全局观，子 agent 当普通工具调用；控制权**不转移**，主人只看摘要 | 适合把 verify 做成工具；代价是主 agent 上下文工程要求高 |
| 5 | **黑板协作（Blackboard）** | 无中心协调，多 agent 围共享状态（黑板/图谱）读写，证据事件触发 | 贴合"证据逐渐浮现"形态，可并行；难调试，纪律要靠协议硬约束 |
| 6 | **FSM 骨架 + 阶段 Agent** | 外圈是确定性代码（阶段状态机），内圈每个阶段一个标准 agent；协调权在 FSM 不在 LLM | 阶段边界=checkpoint，可恢复、护栏可硬化、故障可定位；阶段切分要贴攻击链 |

**两个决策点**：协调权给谁（自身循环 / planner / FSM / 谁也不给）、分工单位是什么（整个任务 / 任务卡 / 阶段 / 证据事件）。六个模式是这两个决策点的组合，不是互斥选项。

**骨架 + 器官选型法**：骨架用确定性代码（FSM），推理用单 ReAct，验证用 agent-as-tool，共享状态用黑板。收敛建议 D 模式 = **B 的骨架 + C 的记忆形态 + 4 的 verify 子工具**。

## 2. 实战剧本分析（js 线突破场景）

### 场景复述
对一个 web 目标渗透，发现端口、js、目录多处疑似漏洞 → 团队多线并行渗透 → js 线发现 bin 文件，下载分析后挖出 CVE，利用后拿到主机 → 其他线收到通知**立即停手**，全队转向主机内渗透 → 进入内网后继续找漏洞、梳理 → 按要求生成报告。约束：客户要求一天内完成，作战室内实时交流、同步。

### 逐节拍映射

| 剧本节拍 | 对应构件 |
|---|---|
| ① 多线并行渗透 | 黑板：多 worker 围同一份 findings 图谱写证据 |
| ② js 线下载 bin→挖 CVE→利用→拿主机 | 单 ReAct 深链（自主 exploit） |
| ③ 其他线停手、全队转向 | FSM 全局跃迁 + 广播 |
| ④ 主机内、内网再挖 | 黑板模型复用，scope 收缩到内网段 |
| ⑤ 生成报告 | report 阶段（此前必须经过 verify） |
| 贯穿：作战室 + 一天期限 | HITL 教练层 + 预算系统 |

### 剧本提炼出的四个架构结论

1. **阶段跃迁必须是显式 milestone**。"已进入主机"= findings 类型 `foothold_established`，经 verify 确认后 FSM 才广播跃迁。纪律硬化为一行代码：**写证据的权力在所有 worker，改变全局状态的权力只在 FSM**。
2. **并行是 P0 而非锦上添花**。一天的 deadline 挖这个工作量，串行单 agent 数学上不成立。
3. **verify 是跃迁的前置闸门**。全队转向的前提是 foothold 被确认；agent 谎报 → 全队白等。claimed → verified 纪律落地处。
4. **深度型强悍被剧本证实**。自主"发现 bin→分析→找 CVE→写利用"是深度型样本，审美偏深度型；v0.1 工具层应给"文件分析 / 受控执行环境"留位置（或至少留扩展点）。

## 3. 护网（HVV）场景的增量约束

### 结论
护网不推翻 D 模式选型（FSM 骨架 + 黑板 + 阶段 agent + verify 闭环），但改变阶段定义、护栏强度、预算粒度。

### 四条增量约束

1. **计划随时变化 → 计划快照模式被判死刑**。护网里计划的保鲜期不超过半小时（防守态势感知在读你）。黑板模式"证据一落、全员立即可见"从优化项变成刚需。作战室口头指挥 = HITL 教练层，频率分钟级 → HITL 必须准实时（推送 + 一键跟进），不能是审批队列式慢通道。
2. **最稳 → 护栏升级为核心资产**。防守方是活的安全团队：打得太吵 = 被通报 = 战役失败。工具层风险分级新增维度——**检测面**（quiet / normal / loud），区别于破坏面；loud 动作默认 `caution` 起步。ctf-agent 的 PolicyEngine 在此场景是主角。
3. **最快 → 预算以小时计 + verify 更严**。串行等待全消灭；误报的代价从"白等一小时"升级为"全队转向 + 暴露意图"。claimed→verified 从工程洁癖变成生存纪律。
4. **报告前移**。护网要即时提交落地证据打分；findings 图谱的产出在 verify 通过当下即格式化为"可上报证据"，report 输出全程持续可用，不再是最后一步。

### 常规渗透 vs 护网约束差
| 维度 | 常规渗透项目 | 护网行动 |
|---|---|---|
| 时间预算 | 天级起 | 小时—天级 |
| 计划稳定性 | 按阶段可排 | 半小时保鲜期 |
| 防守姿态 | 检测被动 | 主动检测 + 追踪 |
| 噪音容忍 | 扫描可接受 | 噪音 ≈ 通报失败 |
| 协调节奏 | 小时级同步 | 分钟级指挥 |
| 护栏目标 | 可审计、可恢复 | 低检测面、verify 更严、证据即时上报 |

## 4. 日常事务：自动化分层与作战剧本（profile）

### 结论
系统从"渗透智能体"放大为"安全智能体工作台"。正确反应不是加更多 FSM，而是两件事：

1. **分层自动化**：不是所有事务都值得上 LLM。
   - **L1 批处理层**（不用 LLM）：端口/漏洞扫描。工具层 + Guard + findings 落库，schedule 可复跑。
   - **L2 单 Agent 深链层**：代码审计、逆向、CTF 单题。单一 ReAct + 深度工具。
   - **L3 战役层**：渗透、护网。FSM 骨架 + 黑板多 worker + HITL，第 1–3 节全部适用。
2. **一个骨架，多份作战剧本（profile）**：每种任务类型是一份配置——阶段状态机定义、工具白名单、风险策略权重、findings schema、HITL 强度。黑板 / findings / Guard / Runner 全复用。兑现"数据驱动配置而非硬编码"红线。

### 事务归位表
| 事务 | 执行形态 | 干预度 | 主要复用构件 |
|---|---|---|---|
| 端口/漏洞扫描 | 纯工具批处理（无 LLM） | 全自动 | 工具层 + Guard、findings 落库 |
| 代码审计 | LLM 深链 + 静态扫描工具 | 低（人 review findings） | Agent Loop + 深度工具 |
| 逆向分析 | LLM 深链 + 受控执行环境 | 中 | 深度型工具 |
| CTF | 单题深链，验证强闭环 | 中高 | Agent Loop + verify |
| 渗透/护网 | 黑板多线战役 | 强控（护网最高） | FSM + 黑板 + HITL 全套 |

### 投资回报观察
代码审计与逆向是"深度型强悍"的高频付费场景——比渗透更日常、可天天练。深度型工具（受控执行环境、文件分析）在 v0.1 至少要占好位置。判据一句话：**动作是否确定 → 用不用 LLM**。

## 5. 漏洞复现环境搭建（repro 剧本）

### 场景
输入一段漏洞信息（CVE / 公告 / PoC 描述），agent 理解后调用容器搭建可触发的靶场。

### 架构定位
- 新剧本 `repro`：信息理解走 L2 深链，容器执行走 L1（确定性、argv 化、过 Guard）。
- 本质：**为 verify 闭环造上游设施**。compose up 成功 ≠ 可触发；启动后必须跑 PoC 冒烟确认"确实处于漏洞状态"——这是 claimed→verified 纪律在靶场问题上的翻版，也修掉了"误报全队白等"的上游根源。
- 是覆盖型与深度型通用的支撑设施：自建靶场让 PoC 复现、审计、CTF 全部受益。

### 构件复用（几乎零新增概念）
1. **verify 纪律**：通过冒烟验证的靶场登记为 findings 图谱 `environment` 类型台账，供渗透 / 审计 / CTF 剧本取用。
2. **Guard 容器策略**：镜像来源白名单、网络隔离、资源限额、防逃逸（不挂敏感卷、不用 privileged）；docker 命令全 argv 化。
3. **验收闭环升级**：repro 成立后，vulhub 验收从"预置环境"升级为"agent 自建靶场"。

### 分级实施
- **v0.1 vulhub 化**：理解漏洞 → 匹配 vulhub 现成条目 → 调起 compose。确定性强、难度低。
- **v0.2 自搭**：读 advisory 的 affected versions 与配置依赖，没有现成条目时自行生成 compose。LLM 深链价值所在，深度型强悍的正剧。

## 7. 智能体工作模式收敛版：统一工作流

### 总命题
一套骨架 + 三层自动化 + N 份剧本。不增加任何新概念，只是把前 1–5 节的东西拼成一个生命周期。

### 统一生命周期（任意任务类型都走这条链）
1. **任务接收**：CLI 输入目标与意图，选定剧本（profile）。
2. **装载剧本**：五样配置——阶段 FSM 定义、工具白名单、风险权重、HITL 强度、验证策略。
3. **FSM 编排**：代码层按阶段推进、派发执行单元。
4. **阶段执行**：L1 批处理动作直通工具层（不经 LLM）；L2/L3 交给 agent worker 深链。
5. **证据沉淀**：黑板 + findings 图谱写入；checkpoint 落 SQLite，任意步可恢复。
6. **milestone 跃迁**（回环）：新证据经 verify 确认后回给 FSM——推进阶段、广播其余 worker 停手/转向，或宣布完成。
7. **交付出口**：report / 可上报证据（护网即时打分）/ environment 台账（repro）。

### 四条铁律
**FSM 管状态 · 黑板管证据 · Guard 管动作 · verify 管真伪。**
agent 只能写证据；FSM 才能改全局状态；Guard 否决任何越界动作；verify 不通过不许当真。

### 剧本矩阵（差异只是 Phase 链配置）
| 剧本 | 阶段链示例 | 层级 | 干预度 |
|---|---|---|---|
| pentest | 外部侦察 → 突破 → 主机/内网（milestone: foothold）→ 验证 → 报告 | L3 | 强控 |
| ctf | 侦察 → 分析 → 利用 → flag → writeup | L2 | 中高 |
| audit | 拉代码 → 静态+LLM 审 → 告警 triage → 报告 | L2 | 低 |
| re | 资产准备 → 静态/动态分析 → 提取 → 台账 | L2 | 中 |
| scan | 直接批处理（无 FSM，纯 L1） | L1 | 全自动 |
| repro | 理解 → 选型 → 编排 → 启动 → 验证 → 台账（见第 5 节） | L1+L2 | 低 |

护网 = pentest 剧本 + 强度开关（检测面分级、分钟级 HITL、证据即时上报、verify 加严）。

## 8. 剧本装载失败与切换的处理

### 原则
剧本里装的是**安全边界**（工具白名单、风险权重、scope 约束），选错剧本不只是效率问题，还是安全问题。
一句话原则：**安全边界绝不静默自适应——宁停不错。**

### 三分支处理
1. **剧本不存在（显式名字未配置）**：fail-fast 拒绝启动，列出可用剧本清单。绝不"找个像的剧本顶上"。
2. **意图推断匹配（未显式指定）**：确定性优先——显式指定 > 意图推断。推断只能给**建议**，且必须过确认闸门（亮出"输入意图 → 匹配剧本 → 依据"，用户确认才开跑）。推断错的代价是整场作业在错误的 Guard 约束下跑。
3. **运行中发现剧本不适配**：agent 无权换剧本（铁律：agent 只能写证据）。写 `playbook_mismatch` finding 提议 → HITL 裁决。裁决换剧本 = 停当前 run、开新 run 并**继承 findings 台账**——findings/黑板是 run 外资产，成果可移植，零新增机制。

### generic 兜底剧本
最小 generic 剧本（单阶段 freestyle、风险策略全保守、所有动作默认 caution），但**永远不会被静默选中**——仅显式 `--profile generic` 或用户在确认闸门亲手选降级时可用。

### 新增待决
- [ ] 推断器实现依据：目标特征启发式 vs LLM 意图分类。
- [ ] 换剧本时 run 交接语义细则（checkpoint 载入 + scope 重新声明）。

## 9. 主流程伪代码与现成框架盘点

前提约定：按用户确认，安全/道德敏感部分（Guard 深度策略、HITL 交互形态）先用占位符标注，不影响流程骨架的完整性。

### 主流程伪代码（harness 骨架）

```python
# harness.py — 主流程（安全/道德部分以 GUARD★/HITL★ 占位）


async def run(task: TaskRequest) -> Report:
    # ①② 任务接收 + 剧本装载（三分支裁决：显式 > 推断确认 > fail-fast）
    profile = await resolve_profile(task)

    fsm: FSM = FSM.from_profile(profile)  # 阶段链 + milestone 触发表
    store: Store = Store(profile.db)  # sqlite: findings · checkpoint · 审计
    guard: Guard = Guard(profile.risk)  # ★占位：本版只做 argv 校验 + 输出截断

    run_id = store.new_run(task, profile)
    workers: list[Worker] = []

    while not fsm.finished:
        phase = fsm.current

        # ③④ 编排：按阶段描述派活——L1 直通批处理 / L2L3 agent 深链
        dispatch = plan_dispatch(phase, store.snapshot(run_id), profile)
        results = await asyncio.gather(
            *(
                [exec_l1(t, guard) for t in dispatch.l1]  # 不经 LLM 的确定性动作
                + [spawn_agent(w, guard) for w in dispatch.l2l3]  # Agents SDK Runner 循环
            )
        )

        # ⑤ 证据沉淀：agent 只能写证据（claimed 状态）
        for finding in parse_results(results, task.scope):
            store.append_finding(run_id, finding)
        store.checkpoint(run_id, fsm)  # 每轮落盘，可恢复

        # ⑥ milestone 回环：verify 裁决 → FSM 跃迁（★verify 本版用 PoC 冒烟占位）
        for f in store.findings(run_id, status="claimed"):
            if await verify(f):  # claimed → verified
                store.mark_verified(f, run_id)
                verdict = fsm.ingest(f)  # advance / broadcast / 完成?
                if verdict.broadcast:
                    workers = halt_workers(workers, keep=verdict.keep)
                if verdict.human_gate:  # 换剧本 / 报警动作
                    await hitl_gate(store, fsm)  # ★HITL 占位

    # ⑦ 交付：只聚合 verified 结论
    report = gen_report(store.findings(run_id, verified_only=True), profile.report)
    store.finish(run_id)
    return report
```

### 智能体内核（OpenAI Agents SDK，约 8 行）

```python
async def spawn_agent(w: Worker, guard: Guard) -> FindingList:
    agent = Agent(
        name=w.name,
        model=w.model,
        tools=guard.wrap(w.tools),  # Guard 过滤后的工具集
        instructions=w.prompt,  # 剧本轮次上下文注入
        output_type=FindingList,
    )  # 结构化输出 → 直接进黑板
    r = await Runner.run(agent, w.mission, context=w.ctx)
    return r.final_output
```

### 框架盘点（2026-10 核实行情）

| 框架 | 能接进骨架的部分 | 不提供、需自写的部分 | 裁决 |
|---|---|---|---|
| **OpenAI Agents SDK** | Runner 循环（单 agent ReAct）、agent-as-tool、`output_type` 结构化输出、handoff | FSM、黑板、findings/verify、剧本语义、Guard | **采用**（L2 内核最轻） |
| **LangGraph** | StateGraph（FSM 骨架）、durable checkpointer（checkpoint 现成）、`interrupt()`（HITL 挂起现成）、Send 并行派活 | 黑板语义、findings、verify、剧本、Guard | **备胎**——骨架可租，语义仍自写 |
| CrewAI / AutoGen | — | LLM 当协调员，违反"确定性协调"铁律 | **pass** |
| Google ADK / MS Agent Framework | — | 云绑定重 | **pass** |
| PydanticAI / Claude Agent SDK | 同类轻量内核 | — | 暂不选 |

真正的差异化价值（黑板/findings/verify/剧本语义/Guard）**任何框架都不提供**——这正是自研的意义。LangGraph 只值得接三个最容易自写的原语：FSM 表、checkpoint、interrupt。

### 两条落地路线

- **路线 A（倾向）：自研薄骨架 + Agents SDK 内核**。FSM/Store/Guard 全自写（一个文件的量级），agent 深度推理用 Agents SDK。骨架 100% 可控，无框架抽象贴合成本。secpt 已有雏形可演进。
- **路线 B：LangGraph 当骨架 + 自写安全语义层**。拿现成 checkpointer/interrupt/时间旅行调试，代价是状态图全按它的抽象走，findings/黑板/剧本仍套在上面。

**我的倾向：A 起步、给 B 留门。** A 的骨架足够薄，将来发现 checkpoint/HITL 自写痛了，可以换成 LangGraph 的 checkpointer 和 interrupt 原语，语义层不用改。

## 10. 第五场景：CTF 脑筋急转弯（misc 类脑洞题）——失速回环

### 场景还原
比赛中 flag 超出常理，常规 probe 全落空，需要"脑筋急转弯"式发散：flag 可能藏在元数据/文件名/谐音/失败报错/多层怪异编码里。普通 ReAct agent 的行为模式高度可预测：对同一批资产**反复 probe 直到上下文耗尽**——这正是骨架要接住的"撞墙"。

### 结论：不换骨架，加一档"发散齿轮"
跟前四个场景同向验证——这个场景**不属于新工作模式**，它是 D 模式既有构件映射的一次复用：

| 现象 | 骨架对应构件 |
|---|---|
| 反复 probe 无新证据 | **失速计**：L2 worker 连续 N 轮黑板无新增 → 写 `dead-end` finding（agent 仍只是提议者） |
| FSM 收到 dead-end | **发散档触发**：同阶段挂起、换任务重派——不是再加个 probe agent，而是换脑子 |
| 脑洞从哪来 | ①**重读黑板**：把未用资产、隐含假设逐条翻出质问；②agent-as-tool 请一个 **idea 顾问**（只发散不执行） |
| 脑洞怎么定真伪 | **verify 筛**：flag 校验/提交接口是天然判定器，脑洞候选一样 claimed→verified 闸门——尤其防 misc 幻觉 flag 转正 |
| 发散也烧完预算 | **HITL 升级**：要 hint 或人工猜；人的猜测同样写回黑板（人是提议者之一） |

### 为什么这几乎零新增
四条铁律原样覆盖：agent 只能写证据（`dead-end` 也是证据）、FSM 才能切档、verify 判真伪、HITL 只在 FSM 收到 human_gate 时介入。CDN 起点的一次"发散重启"= FSM.attack 阶段内部的一个子状态跃迁，全文只在 profile 里加一行配置：`stall_threshold: N`。

### practice：发散档给 worker 的典型三件事
1. 把黑板里"我没信过的信息"全部翻一遍——题面描述逐词、文件名、时间戳、字符串表
2. 调 idea 顾问工具拿脑洞清单（audio spectrogram / zsteg / unlikely encoding chain / 谐音梗），逐个生成 tried-assertion
3. 每条脑洞交给 verify 冒烟（flag 校验器）过滤，过筛的才进台账亮点

### 新增待决
- [ ] 失速判定条件细化：轮数 vs 黑板证据增量的组合条件（纯轮数会误伤慢审计线）。
- [ ] idea 顾问 persona 库放全局还是剧本内（misc 脑洞库几接近通用，可能与剧本无关）。

### 逐家映射到 D 模式

**CyberStrike**：摸到三块——methodology engine（v1.1.14）≈我们剧本/FSM 的原始版（跟踪 coverage、避免重复扫描）；3-gate 确认≈verify；技能签名 提出了一个我们没有的维度：**profile/技能供应链完整性**。值得偷：Ed25519 签名技能、漏洞按 endpoint+attack_vector 去重、防 403/公开端点 FP 的 prompt 硬化。

**ARTEX**：摸到黑板——资产-漏洞以图累积贯穿全程（比我们 findings 流水表多一层结构），多突破路径并行正是我们黑板多线 worker 的形态实证。反面教材同框：无 Guard/HITL 被国家级滥用。值得偷：**findings 从流水表升级为图**；引以为戒证明我们"可控"方向的必要性。注：Artex Pro 企业版主打"全程可控、运行稳定、结果可追溯"——市场在验证确定性协调方向。

**dsh-redteam-mode**：本质是挂在 coding CLI 上的"剧本包"。六角色≈phase worker 角色表，技能包≈profile 白名单，"一句话拉起"≈意图推断装载（我们第 8 节分支 B 的落地现状）。值得偷：**POC 知识库作为可检索技能**——正好是 verify 冒烟的弹药库。短板：协调全靠 prompt，无 FSM/Guard。

**ZCode**：执行模式选择器=按任务风险选 agent 权限等级（安全/自动/全自动），命令/文件改动/网络访问先在任务里可视化再放行，高权限下风险提示常驻。这是 **profile 干预度三档的现成 UI 范本**，比我们的文字描述具体。

**Codex**：最成熟的"L2 内核+Guard 分级"样本。工具执行统一走沙箱+审批分级，与我们 Guard 分档设计同构；AGENTS.md≈profile instructions 注入。它证明单 agent ReAct + 分级审批在生产可用。

### 横向结论
1. **没有一家拼全**：FSM 骨架+黑板+verify+剧本+分级 HITL 的完整语义层，每家最多摸到一两块。这再次确认自研语义层是差异点而非重复造轮子。
2. **两极分布**：要么"强悍但失控"（ARTEX/CyberStrike），要么"可控但浅"（ZCode/Codex/dsh 的宿主）。我们正定位为中间的空白：**可控的强悍**。
3. **可平移的三件真金**：①CyberStrike 3-gate 协议细读（对照我们 verify 设计）；②ARTEX 的图黑板；③ZCode 执行模式选择器（HITL UI 落点）。加一件我们自己补的：CyberStrike 的技能签名。

## 12. 关键修正：通用 agent 能把安全任务做好——那语义层剩下什么

### 用户观察
ZCode/Codex 这些产品不是做安全的，但把安全任务交给它们，一样做得很好（dsh 也实证了：通用 coding CLI + 剧本包 = 能拉起红队）。

### 承认这个判断对在哪
**L2 单 agent 深链这一层，通用 agent 已经是合格到优秀的器官。** 如果我们按 Agents SDK 从零写 Runner 循环去硬攀 Codex 的沙箱/上下文管理/工具成熟度，是在造一个更差的轮子。

### 再追问一步：它"做得很好"之后缺什么
拿"已经打完 80 分"之后的问题倒推，安全作业真正难的不是单点智力，是**收尾**：

1. **任务结束时的状态形态**。通用 agent 跑完渗透产出的是会话记录（或 markdown）。会话不是台账——claimed/verified 状态、误报剔除、verified 聚合全埋在聊天流里，而实战场景的交付物恰恰是"可追溯报告"。
2. **守边是攻防语义，不是通用概念**。ZCode/Codex 的权限分档为"改错代码"设计；"scope 界外不扫"、"突破成功全员停"、"高危分钟级放行"只能靠 prompt 承诺——会话里最靠不住的东西。
3. **多线协同没有裁决者**。js 突破后全员转 host 是跨会话裁决，通用产品没有承载全部上下文的"黑板"。

注意：这三条没有一条是"干不了"，全是"干完了没有可靠收尾"。

### 架构修正（对路线 A 的精化）
- **L2 执行器官可插拔**：`spawn_agent` 是接口，多实现——Agents SDK 进程、拉起 Codex CLI/ZCode 子进程均可。肌肉在外，复用最强的心脏。
- **自研语义层收窄到通用 agent 三条不提供的能力**：台账/verify 收尾、攻防语义 Guard、多线协同 FSM/黑板。三个器官一个不少，但单点执行力不自造。
- 结论一句话：**骨架和器官是分层问题，不是二选一**——激进自研（CyberStrike/ARTEX 方向）缺 Organ 基础，纯通用产品缺骨架。我们在中间：**薄骨架 + 可插拔器官**。

### 新增待决
- [ ] spawn_agent 接口契约：结构化输出（FindingList）在子进程形态（如 Codex CLI）下怎么拿到——文件协议 vs stdout 解析 vs MCP。
- [ ] 用 Codex/ZCode 做一轮"通用 agent 渗透收尾"实测，验证"80 分之外缺什么"的判断（比纸上分析强）。

## 13. 安全架构视角：通用 agent（Codex/ZCode）的功能模式解剖

### 问题
通用 agent 不是安全工具，但其安全架构恰是我们 Guard/HITL 最成熟的参照系。拆它的"智能体功能模式"。

### 五层信任链

1. **建议-执行分离**：Codex 的 plan 模式、ZCode 的"先可视化动作（命令/文件改动/网络访问）再执行"——agent 永远是提案者，副作用必须跨过裁决闸门。这是我们"agent 只能写证据 / FSM 和人改状态"铁律的产品版。
2. **能力分级（默认最小权限 + 风险可视）**：Codex approval 从 untrusted/read-only 到 auto/full 分档、默认读沙箱；ZCode 执行模式选择器按任务风险选权限，分档越高风险提示越常驻。能力是旋钮不是开关，默认最保守。
3. **硬隔离防线**：Codex 敢开全自动是因为有 OS 级沙箱（Seatbelt/Landlock）+ 默认断网兜底；ZCode 文档明说"权限控制不是 sandbox、不提供隔离"（承认边界）。启示：**自动挡的胆量由隔离层决定，不由 prompt 决定**。
4. **diff 即证据**：Codex 产出是文件系统 diff 而非直接生效——人审 diff 就是人审证据，天然审计链。与我们"findings 台账当证据"形态不同、原则同构（agent 只写证据，人只审证据）。
5. **上下文信任锚**：AGENTS.md / 项目约定注入区分"环境可信指令"与"agent 自主发挥"——即我们 profile 的 instructions 注入。

### 一句话概括
**单 agent + 分级信任 + 动作可视化 + 人工最终裁决 + diff 即证据。**

### 威胁模型差异（为何能当 L2 器官、当不了 L3 骨架）
它们为"代码损坏/秘密泄露/误操作"设计；攻防语义（scope 越界、战果广播、误报入账、多线裁决）不在其威胁模型内。这是第 12 节结论的另一面。

### 对我们设计的直接影响
- 验证：干预度三档（ZCode 范本）、plan/approval 分离（同构于我们的 propose/act）、diff/findings 作为唯一审计面。
- 新暴露的低估点：**"敢自动"是沙箱给的**——Guard v0.2 的容器/沙箱背书优先级应提高，纯策略约束只能支撑审批档。

### 新增待决
- [ ] Guard 分档与隔离层的绑定关系：全自动档必须建立在容器/沙箱背书上（写入 profile schema 约束），纯 prompt 约束允许的最高档 = 审批档。

## 14. 小白版：整套架构讲明白（架构审核总结）

（应"小白也能看懂、大道至简"要求，把 1-13 节收成一段话+一张图；行话全部翻成人话）

### 一句话版
它是一个小型安全团队的自动化版本：**总指挥按剧本派活，干活的只交"小票"，验收员验过才算数，危险动作问你才许做。**

### 六个角色与存在理由

| 图上角色 | 行话 | 为什么必须有 |
|---|---|---|
| 总指挥 | FSM | 干活的不能自己决定"下一步去哪"，否则几个天才乱跑、相互踩脚。总指挥不聪明，但**从不忘记、从不撒谎、从不拍脑袋** |
| 剧本 | profile | 渗透/护网/CTF/搭靶场是四种干法，但骨架是同一个；换任务=换一份配置，不是换一个程序 |
| 干活成员 | agent | 真正聪明的部分（审计、exp、读代码）；像可插拔的肌肉，Codex/开源内核都能装 |
| 账本 | 证据台账 | 干活的只能写"我以为/我发现了的小票"声称，不能改账本、不能直接下命令——出了问题查有据可依 |
| 验收员 | verify | 小票只是声称，PoC 点一把火才算数——挡住夸大和臆测 |
| 护栏 + 你 | Guard/HITL | 机器拦一道危险动作，拿不准交由人拍板——**担责的人永远是人** |

### 一次任务从头到尾（大白话）
1. 你说打这个站 → 系统挑一份对应剧本；
2. 总指挥翻开剧本："第一步先侦查"，把活派给几个干活的；
3. 成员有突破只能交小票 → 总指挥对账发话"全员转战主机"——不许先斩后奏；
4. 高危动作放行与否在你手里；
5. 收尾报告只从验真账目里汇总，不掺杂猜测。

### 大道至简的证明
整个系统运作时只有一个循环：**派活 → 收小票 → 验真 → 总指挥看里程碑再派活**。前 13 节的十个场景（渗透、护网、审计、逆向、CTF、搭靶场、脑筋急转弯……）全部落在这条环上，只换剧本和参数，没有第 7 个部件——这就是为什么架构是收敛的、可迁移的。

### 视觉件

## 15. 小白版二问：剧本怎么选？不选行吗？

（对应第 8 节三分支的小白问法，结论同一套机制）

### 怎么选：三种方式，可靠性从高到低

1. **你直接点名**（最可靠）：任务单上写明"用护网剧本/搭靶场"——照办不多想。真实作业基本如此。
2. **系统猜，你拍板**（默认通路）：不点名时看任务描述线索（"护网""CVE-XXXX""flag"），猜一个后**把选项摆给你的**：像 X 剧本、证据这三条线索，同意才装。**猜可以自动化，装必须人点头**——装错可能白干整天甚至越界。
3. **宁停不错**：线索太模糊、几个剧本都像又都不像——停下来问人，不挑一个蒙着干。

### 不选行吗：三种情况

- **你不点名 = 行**：走"猜+确认"通路，代价只是多点一次头。
- **连猜都猜不出 = 行，但停**：报错说明缺什么线索，补一句就行。停下是设计，不是故障；瞎猜着干的渗透智能体才是故障。
- **干到一半发现剧本不对 = 停，且严重一档**：比如以为是 CTF 结果是真实客户资产——任务本身错位，属红灯级别。所以第三类在实践中最险，"确认闸门"永远是第一道防线。

### 一句话收口
**可以不选（系统帮你猜），但不能不确认（你必须点头）——点头的动作永远省不掉。**

### 实战考题："帮我渗透某一个 web，找到 flag" 用哪个剧本？

线索打平的典型案例："渗透+单一资产"指向 pentest，"flag"指向 CTF。而两个剧本的差异是**要害配置级**的：

| 差异点 | pentest 剧本 | CTF 剧本 |
|---|---|---|
| scope 约束 | 界外不碰（可能是真资产） | 无 scope 敞开打 |
| Guard 档位 | 审批档为主 | 自动档为主（sandbox 背书） |
| 验证 | PoC 冒烟 + 影响面 | flag 校验器直判 |
| 收尾 | 报告（复盘） | flag 值（交卷） |

系统行为：**确认闸门亮灯**——端出双候选卡 + 一个裁决问题："这个 web 是谁的？"一句答案同时定死 scope/Guard/verify/收尾四件事（自己的靶机 → B；客户资产 → A，并声明越界线）。

**不答时的硬默认**： 采用更严格的一份（pentest 装备与流程），而不是 A/B 各跑一半——**default = stricter, not smarter**。

**洞口收敛**：这就是悬置项"推断器实现依据"的完整答案——线索表 + 候选差异卡 + 一个裁决问题，全部可先用关键词规则实现，不需要 LLM 分类器。

- [x] ~~推断器实现依据~~ → 已收敛：关键词线索表起步，候选差异卡+一个裁决问题是其全部形态。

## 16. 用户拍板：任务就是任务——剧本库降级为"进场三问"

（用户观点："我倾向于边想边干，不管什么任务，结局都一样"）。此一主张直接修正 15 节之前的"N 份剧本菜单"设计。

### 主张一："结局都一样"——对，架构本来已证明
所有场景走同一循环（派活→收小票→验真→再派活），结局同一形态：**Verified 结论 + 想要的交付物**（flag/报告/环境/上报事件）。机制同一，入场就不该摆 N 份剧本菜单。

### 主张二："边想边干"——对一半，对半上锁
自由该发生在**阶段内**。FSM 收成三段：

```
进场（三问+记边界）→ 干活腿（边想边干，agent 自主）→ 出场（出口清单强制）
```

- **进场三问**——把"剧本差异"全部压缩成参数实例化，不再有"选剧本"这回事：
  1. 目标是啥？（找 flag / 出报告 / 搭环境…）
  2. 资产是谁的？（直接定死越界线和护栏强度——15 节那题的答案就包含在这问里）
  3. 快到什么程度 / 有没有人盯？（护网=快+盯紧；日常=从容+多验证）

  大多数情况一句话就带过（"打这个站找 flag"两问答案就藏里面），不需要填表。
- **干活腿**：agent 边想边干。FSM 只在两处出手：
  - **里程碑**（如"进了主机"要广播停线）
  - **撞墙**（失速换思路，第 10 节机制）
  平时绝不指手画脚。
- **出场清单**（强制，不随"边想边干"）：验真的账全交了吗？高危动作全审批了吗？交付物对得上任务目标吗？

### 唯一不能"边想边干"的东西：边界
进场时记录的越界线（scope）/ 工具白名单 / 栏杆强度不会因 agent 想扩大战果而漂移。**边想的自由，到手为止，不越线。**

### 架构影响
- 原"N 份剧本 + 选型 + 推断器 + 确认闸门"瘦成"**通用骨架 + 进场三问**"。
- 推断器降级为三问的**预填器**（一句话填答案，超过一条歧义才亮题）。
- 护网减速鞋（回波、高危即批）等不再需要单独剧本——它们本来就是参数实例，不是白名单另一份菜单。
- 待决项继续收干：~~剧本选型~~、~~推断器~~已并入三问机制。

### 待随之修正的前文
- 第 7 节"六剧本矩阵" → 改读为"参数实例差异表"；
- 第 8 节"三分支装载" → 保留"超界面即问"，但优先通路变为"三问预填 + 亮题"。

## 17. 小白版三问：FSM 是什么？有模型吗？

### FSM 到底是什么
有限状态机 = "处于什么状态 + 遇到什么事跳到哪个状态"的**查表卡**。生活实例：红绿灯（绿→黄→红，绝不即兴）、电梯、快递订单状态（下单→揽收→运输→签收，不能跳步）。

我们架构里的总指挥就是一张表（进场→干活→出场 + 两个出手时机），展开形如：

```
进场中     三问答完            → 干活中
干活中     小票验真命中里程碑   → 停线广播，仍在干活中
干活中     连续撞墙            → 换思路，仍在干活中
干活中     目标达成/预算烧完    → 出场检查
出场检查   清单全过            → 结束（有问题则停给人看）
```

### "有模型吗"的两层回答
1. **它不是智能模型（不是 LLM）——恰恰相反**。FSM 没有大脑，就是代码+表。用它正因为：不幻觉、不忘事、不能被 prompt 说服放行违禁动作、每次跳转有据可查、行为完全可复现。**LLM 负责聪明，FSM 负责不犯低级错误**——聪明部分会犯错，所以必须圈在不犯错的东西里。
2. **现成物很多，三层都有**：
   - 数学模型：自动机理论（1950s 成熟）；
   - 软件工程形态：UML 状态机 / statecharts（Harel, 1987）；
   - 可用库：Python `transitions` / JS `XState` / LangGraph 的 StateGraph（本质是带检查点的 FSM——第 11 节选它当备胎的原因）。

### 落点
骨架自研（约两百行），`transitions` 当垫——因为表里有我们自己才有的词条：**milestone 触发、失速判定、出场清单**；库只负责"跳转不犯错"，词条内容是项目自己的。

## 18. 小白版四问：谁负责智能体？FSM 怎么承接它？

### 智能体 = 四件套循环（不需要我们发明）
```
大脑（LLM）＋ 手（工具）＋ 循环（边想边干）＋ 记性（上下文）
```
一个回合：看任务→选工具→动手→看结果→再决定……直到干完。Agents SDK / Codex / ZCode 都是现成的循环实现（即第 12 节"可插拔器官"）。

**我们负责圈活动空间，不负责教它聪明**——聪明是模型厂商的事，发单收单是我们的工程事。

### FSM 承接智能体：只有四种交往（工地总管对施工队）

1. **发单**：任务单只装本单所需（目标+边界+黑板摘要），**不发全量账本**——防被无关信息带偏、防未验证猜测污染 agent；
2. **收单**：agent 只能交**结构化小票**（FindingList），不许自由写状态、不许自己宣布"我赢了"；小票落账本，验真才算数；
3. **闸门夹缝里干活**：每次伸手（命令/网络/高危）先过 Guard——白名单内放行，否则拦截或弹人；
4. **掐表**：FSM 持有时钟与预算——超时/超支/连环撞墙，可随时拦停 agent 循环、换人、或收工。**agent 是可被叫停的承包方，不是自主运转的小社会**。

一句话：**FSM 看不懂也不看 agent 的内心戏，只认小票和闸门记录**——所以它"笨"却能管住一屋子聪明人。

### 对应第 9 节代码
`spawn_agent` 八行即第 1-3 条实体：发单（`w.mission`）、收单（`output_type=FindingList`）、闸门（`guard.wrap(tools)`）；第 4 条掐表由外层 asyncio 超时 + 预算账本承担。

## 19. 架构评审：用户流程图（v0.1 需求文档）vs 已收敛骨架

（对象：pentest-agent-goals-requirements-v0.1.md 的流程草稿——主LLM 理解任务边想边干/读经验库 → 列规划 A/B/C → 调工具+worker 多线程 → 状态实时更新可灵活调整 → 检查每条完成否 → 完成则结束；收尾双 LLM：LLMA 结构化报告、LLMB 沉淀经验）

### 先给公道：这张图就是 D 模式的"干活腿"
主 LLM 边想边干、多方案规划、灵活调整、worker 分角色多线程、双 LLM 收尾分工——逐行映射到已收敛骨架无一处冲突；其中"LLMB 沉淀经验"反而是讨论中一直偏薄的一笔。

### 没有想到的缺口（按严重度排）

**第一档：缺真伪与代价**
1. **无验收员**：「每条规划是否完成」查的是计划完成度，不是结论真假。没 verify，臆测会流入报告；更险的是经 LLMB 沉淀进经验库后，**下个任务再读入——错误自我繁殖**（图中第 3 行与第 22 行闭环，最危险的一条）。
2. **无账本**：「状态实时更新」存在哪？会话关了即失。需要任务外存活的台账（小票：谁报/状态/验没验）——报告数据源、审计证据、断点续跑存款三合一。
3. **无闸门**：worker 伸手无拦截层，过界扫描/打错资产无从防御与追溯。

**第二档：缺刹车与方向盘**

4. **无人**：「灵活调整规划」的调整人默认只有主 LLM 自己；护网红灯/方向裁决/资产归属这类问题必须留人插口。
5. **无刹车语义**：「没完成→继续」是死循环条款——超预算/卡死/崩溃都要有合法出口并如实进报告。
6. **无里程碑语义**：「进主机全员转战」不是"某条规划没完成"，是方向变了——需要黑板+广播停线，图缺此环。

**第三档：小型但会疼**

7. worker 输出无格式约束（要结构化小票）；
8. 经验读入无来源标记（知识库中毒风险/prompt 注入）；
9. 报告应从台账取数（verified only），不让 LLMA 凭记忆复述战场。

### 一句话概括缺口
图画的是**顺流**（怎么干活），缺的全是**逆流**：**假的怎么挡（verify）、错的时候怎么办（刹车/人/出血口）、危险的时候怎么拦（Guard/边界/账本）**。

### 融合方案（不动用户直觉，只加骨架）
主 LLM 保留「边想边干 + 提规划 A/B/C」的提案权 = 干活腿的内部；骨架（账本/闸门/验收员/刹车/人）兜住它的每次伸手。用户图 + 14-18 节骨架 = 完整版。

### 新增待决
- [ ] 经验沉淀条目的最小可信字段：来源 run、验真状态、命中率（防范幻觉自我繁殖）——经验库 schema 是 profile schema 之后的下一个落笔点。
- [ ] LLMB 沉淀时机：纯收尾做 vs 边干边沉淀（撞墙时即刻入库）——涉及 run 中断时经验是否丢失。

## 20. ZCode 的三问答案（幻觉判定 / 刹车 / 拦危险）

（诚实边界：按产品级公开功能判断，非源码级。）

### 怎么判断幻觉？——不判断，改为验证
代码场景有天然裁判：**编译/测试/diff 这些世界真相**。LLM 说"做完了"，ZCode 只认执行结果——编译失败退回继续，测试绿才算完，证据（diff/测试输出）自动留档。幻觉在"与世界对撞"的环节被打掉；谎报"已运行测试"仍可能发生，但闭环会把谎报拽回来重干。

映射：白盒裁判（编译/测试）→ 我们裁判 = **PoC 冒烟复跑**（第 5 节已定）；claim 无可复跑证据 → 退回或标 unverified。

### 怎么刹车？——三样
1. **干预度选择器**：全自动 / 每步审批 / 计划先行——进场时选，运行中可调档；
2. **预算上限**：token/时间/步数封顶，烧完自停汇报；
3. **随时打断 + 断点恢复**：刹得住，也放得回去。

### 怎么拦危险？——三样
1. **沙箱打底**（文件/进程/网络隔离，先缩圈再谈放行）；
2. **命令分级 + 白名单**：安全命令自动过，高危命令（删文件/改系统/外连）**明确弹窗要人点**，不靠模型自觉；
3. **高危先看小样**（dry-run/预览确认后真跑）。

### 三件可平移
| ZCode 机制 | 落到我们 |
|---|---|
| 执行当裁判、谎言闭环退回 | verify 接 PoC 冒烟，claimed→unverified→重干 |
| 干预度三档选择器（含运行中调档） | profile schema 的 HITL 强度字段 |
| 高危白名单 + 明确弹窗（不靠模型自觉） | Guard 分档（与第 13 节结论同向：敢自动必须沙箱背书） |

## 21. CyberStrike 的三问答案（幻觉判定 / 刹车 / 拦危险）

（定位更新：开源终端渗透 agent，TUI，接入现有 LLM 订阅（Claude/GPT/Ollama）。本轮经检索核实，比第 11 节二手盘点更立体；按产品/文档级认知判断。）

### 怎么判断幻觉？——真相拆成两路来源

1. **流量当真相（Vortex）**：内置 HackBrowser 抓 HTTP 流量，Vortex 对每个请求套规则、标异常。claim"注入打了"，流量里没有就是没有——**事件层的说谎最难**（黑盒侧的世界真相，类比 ZCode 的编译/测试）。
2. **专家代理分诊**：wstg-agent 按请求信号派 13 个 WSTG 专项代理（注入/认证绕过/IDOR/会话等），各按方法论清单出**结构化结论**（schema normalization 保证跨厂商模型统一格式，claim 不合规进不了流水线）。
3. 加上第 11 节三闸门，全链为"声明→证据→复核"。

**方法论注入（Intelligence Layer）**：把 OWASP 方法论/漏洞模式/攻击链推理注入每次模型交互，底层模型不内置也行——与 v0.1 文档"主 LLM 读经验库"同构，工程化答案是**知识注入发生在发单时，不靠模型自己想起来读**（印证第 18 节 FSM 发单只给本单上下文）。

### 怎么刹车？——弱项（诚实结论）
自主运行是它的设计目标（"without constant human prompting"），干预度选择器/预算封顶没有产品级机制，实质刹车只有 skill manifest 里的 Risk-Tier/Scope 声明（靠作者自觉）。印证第 11 节"强悍但失控"的极点判断。

### 怎么拦危险？——绝活：执行体分离 + 供应链签名

1. **Bolt 远程执行**：危险工具不在本机跑，部署到 VPS/容器/靶场，本机发 MCP 指令（Ed25519 认证）；"One CyberStrike, many Bolt servers"——多隔离环境并发派活。隔离思路是**不在本地跑**。→ 第 13 节"全自动档必须背书"由此拿到第三种背书方式：不只有容器沙箱，**远程无状态执行体 + 一次性环境**也算。
2. **技能供应链签名**：SKILL.md 需最小权限清单 + Ed25519 签名 + content_hash + 依赖哈希锁定 + Risk-Tier/Scope 声明。对应 OWASP Agentic Skills Top 10 的 AST02（供应链投毒）应对——正是第 11 节说要补进第 8 节装载安全的那件事，现在有了完整范本。

### 对比 ZCode 一句话
ZCode 强在**刹车**（三档/打断/预算），CyberStrike 强在**危险隔离**（执行体分离+签名）——互补，合成 schema 的"HITL 强度 × 隔离背书"两层。

### 新增可平移清单
- [ ] Bolt 式执行体分离（远程/一次性环境跑高危）——进 Guard 背书机制；
- [ ] 技能包签名（Ed25519+content_hash+最小权限 manifest）——进 profile/技能装载安全；
- [ ] Vortex 式规则化流量真相——黑板可加"客观事件流"层（LLM 小票之外的独立取证路）。

## 22. ARTEX 的三问答案（幻觉判定 / 刹车 / 拦危险）

（经检索核实：mhtsec/ARTEX，开源多智能体自主渗透框架，定位隔离靶场；反面教材——2026 年 9 月 Storm-0940 武器化它攻击 2200+ M365 租户（ConnectWise 供应链），初始访问到特权访问 <3 小时，微软官方博客 10/21 确认。）

### 怎么判断幻觉？——锚进双图 + 流量真相
招牌是**双图架构**：**资产图**（root域/子域/IP/服务/应用/端点——跨任务共享的资产事实源头）+ **探索图**（记录哪些节点哪些 agent 真的测过，力导向布局可视化覆盖面）。
判定逻辑：claim 必须锚进图——"我测了 X"在探索图可查实；叠加**MITM 全流量录制**当事件真相（与 CyberStrike Vortex 同思路，但 MITM 双向而非浏览器旁路）。
**诚实结论**：锚定+取证强，但同样没有独立 verify/复盘模块；三家中只有它"已测覆盖"记账最深。

**意外收获**：探索图按设计就消灭"反复 probe"失速——想重扫时图里记着"这条边这个 agent 已测过"。与第 10 节失速计用黑板判重同方案。

### 怎么刹车？——把刹车外包给"隔离实验室"
- 按任务配置 worker 规模（per-task worker config）；
- HITL 审批关；Dashboard：token 消耗/活动流实时观测；
- 核心刹车逻辑是外壳定位——"只许在隔离靶场跑"。**但这是纪律性边界而非结构性边界**（限制部署者，不限制软件暴力）。

### 怎么拦危险？——隔离+审批+全流量，但被现实打了脸
拦危险三件：隔离实验室定位、人审批关、全流量录制（审计）。**Storm-0940 战役证明没拦住**——国家级行动者拿它自动化攻击，2200+ 租户、<3 小时、无需人盯守。

**给我们最重的一条**：ARTEX 的失败不是缺哪个模块，而是**把约束放在"给使用者看的说明"里而不是"代码护栏"里**。我们的 scope/Guard 必须是代码强制——文档说明只能锦上添花，不能是唯一一层。

### 新增可平移清单

## 27. 架构现状总览（截至第 26 节的收敛态）

**一句话：薄骨架 + 可插拔器官**——FSM 是骨头，四种 LLM 与 agent 是器官，sqlite 黑板是血液，verify/Guard/HITL 是尚未焊完的立柱。

### 五层结构
1. **协调层——FSM 骨架**（约两百行，自研）：三段机进场→干活→出场；进场三问替代剧本库；两出手时机（milestone 广播/撞墙换思路）；唯一锁死=边界（profile.toml 每任务显式）。
2. **智能层——FSM↔agent 四动作接口**：发单 `w.mission`（只给本单上下文）/ 收单 `output_type=FindingList`（结构化小票）/ 闸门 `guard.wrap(tools)` / 掐表（超时+预算）。LLMC 同走此套：代码可判触发、只提案不裁决、交小票。
3. **事实层——黑板 sqlite**：findings 台账（claimed→verified）、双图（资产图+探索图）、审计日志、经验库（跨任务）。append-only，所有角色（含教练/报告/总结）只交小票不改状态。
4. **收尾层——双 LLM**：LLMA verified-only 报告；LLMB 沉淀经验（三家皆无的独家管道）；异常出口（刹车/超支/撞墙）同走此回路。
5. **立柱与地基**：verify（PoC 冒烟复跑）/ Guard（命令分级+高危弹窗）/ HITL（CLI 先上）三柱语义已定、代码未落=剩余全部缺口；第 25 节 9 件工程产物为开工地基。

### 核心代码骨架（Go 伪码，第 9/18 节定稿）
```go
for fsm.InPhase("干活") {
    w.Mission(buildContext(blackboard), guard.Wrap(tools))   // 发单+闸门
    r := <-w.Output                                          // 收单小票
    blackboard.Append(r)                                     // append-only 落账
    if fsm.Stalled()  { fsm.Redirect() }                     // 撞墙换思路
    if r.Milestone  { fsm.Broadcast(r) }                     // milestone 广播
}
```

- **已定稿✓**：三段机/进场三问/两出手时机/四动作接口/LLMC 三件事/双图主干/LLMB 管道/配置两分类。
- **待落地◐**：verify/Guard/HITL 三柱 + 双图表 vs 图形态 + 异常分支图等工程地基。

4. 单工具冒烟：一靶机一工具一 worker 跑通全闭环。

### 打通验收标准
跑完一次后 sqlite 中可找到五样：小票、双图状态、一条 claimed finding、一条带 environment 标记的经验、一份 LLMA 报告。五样齐=流程通。

## 34. 三问三解：上下文 / 工具半结构化 / 失速（附业界对照，经检索核实）

### ① 上下文 = 黑板读出器 + 账本翻篇
全量永远在 sqlite；主LLM 每轮只领"注意力包"（目标+本单+双图摘要+最近N条小票），大小恒定。账本满→旧段压 5 行摘要，原文留库。
业界同构：Claude Code auto-compact（LLM 压缩+滚动缓冲）+ 子代理上下文分段（CyberStrike 13 专家=天然切片）；反面：Strix 把 nmap 原文直接喂回上下文=长跑缺陷。

### ② 工具半结构化 = 漏斗三层
原始 stdout 永远落盘不进上下文；进上下文的只有结构化小票（host/port/service/verdict+evidence 指针）。
层1 工具自带开关（nmap -oX）；层2 适配器插件每具一文件（parse_nmap→JSON，业界范本：Kali MCP parse_nmap、pentestcode 把 XML 直接写成战役状态）；层3 兜底降级（正则+LLM 摘要器）。新工具=加一个适配器文件。

### ③ 失速定义与归属
失速=重复劳动无新增覆盖（空转非慢）。**Go 失速计每轮收盘固定跑**：Δ覆盖/小票hash去重/同目标同命令重复；连续 N 轮 Δ=0 拉铃。
分工：**Go 判零拉铃（算术可测、不自我宽宥），LLMC 只负责拉铃后提案换思路**——算术与表决分开。

Sources: arXiv 2604.14228（Claude Code 设计空间）；Claude computer-use 最佳实践（compaction）；Strix 评析（喂原文反例）；Kitploit pentestcode（XML→战役状态）；LobeHub Kali MCP（parse_nmap 范本）。

## 36. 我们的记忆模型定稿（三层+一表+质量循环）

**三层**：工作记忆=注意力包（读出器现打包，跑完即弃）/ 战役记忆=sqlite 黑板（本 run 账本，跨 run 即归档）/ 长期记忆=experience 表（唯一跨 run 记忆体）。

**experience 表 schema 八字段**：scene_tag（场景签名=检索钥匙）/ content / commands（argv，禁 shell）/ environment（lab|prod，靶场经验禁原样搬家）/ verify_state（verified|claimed，只判真当正典）/ source_run_id（溯源）/ useful_count（命中率）/ 时间戳。

**读写循环**：写=LLMB 收尾沉淀唯一写口（声称=claimed）；读=读出器+发单时 scene_tag 匹配 top-K。质量靠用出来：引用且派上用场 useful_count+1；连续 0 命中降级不进包；本 run 复核命中经验可升 verified；淘汰/改版留审计。
三态进包规则：verified=正典；claimed=只当线索（commands 字段隐藏，给思路不给命令）；降级=不进包。

**v0.1 切法**：现在做=表建齐+LLMB 写入+scene_tag 关键词 sql 检索；后做=Qdrant 向量层+质量循环自动化。
**红线**：记忆只是读出器的一个配方（进注意力包），绝不直插 agent 上下文当编辑器——记忆不是第二个引擎。呼应第 35 节：Letta RAM/硬盘范式与 MemoryLake 治理三件套（environment/溯源/命中）均已本地化实现。

## 37. 工具结构化输出实施版（第 34 节漏斗的施工规格）

**统一 ticket schema（全工具一套）**：run_id/step_id/tool/cmd_argv（argv，禁 shell）/status/exit_code/raw_ref（原始落盘指针，绝不进上下文）/parser（adapter:nmap-xml | regex | llm，置信度标注）/events[]（kind=service|finding|error，host/port/svc/detail）/summary（一行人话，供注意力包）/ticket_hash。

**六条铁规矩**：①原始全量先落盘，票里只放 raw_ref；②events 上限截断；③parser 字段必带；④LLM 摘要器只兜底不出场（省钱防改写幻觉）；⑤kind=finding 锚 raw_ref 可回溯；⑥一票两档信息——summary 给主LLM注意力包，events 给 worker/探索图。

**适配器接口（每工具一个 Go 文件）**：`Match(tool,argv) bool` + `Parse(raw)→Ticket`；层1 自动注入结构化开关（nmap 补 -oX）；层 2 解析 XML/JSON；层3 兜底=正则+LLM 摘要器（parser:"llm" 低置信度入双图，将来可重跑升级）。

**三坑**：stderr/exit_code 不许丢（扫描器常半跑完）；一调一票（与双图步长齐平）；worker 不许直读原始文件（必须过读出器，漏裸输出照样炸上下文）。

## 40. v0.1 图纸三零工（用户本轮提交"直接改"）
① input 加 goal 必填注释（缺 goal 启动即拒）；② 完成分支插出场清单（账本交齐/verified 清点/交付对目标）+ 异常降级收尾分支（LLMA 半场报告+LLMB 失败经验标 environment=lab）。经此一改，图纸逻辑环全闭合，仅剩工件清单（第 39 节表）待落笔。

### 41. 修正：goal 分模式（用户纠偏）
**goal 非必填**：无 goal → 正常对话模式（答问/探索/咨询，不强制规划闭环、不逼出"完成"）；有 goal → 渗透任务模式（规划闭环+出场清单+异常收尾）。两种模式共用同一入口和主循环——边界=goal 字段存在与否。这比"启动即拒"优雅：入口不把人挡在门外，只决定走哪条道。

### 42. 修正：一步=LLM 一次循环（用户纠偏）
一步 ≠ 一次工具调用，而是**主LLM 一次循环**（可调用多个工具）。这才符合 ReAct/Agent loop 惯例：每个循环里 LLM 自己决定调几个工具、怎么组合。此前"一次工具调用"的定义过窄，会把"调 nmap+nikto 组合"这种一步拆成 N 步——预算虚高，失速计误判。改后：工具调用是执行细节，循环才是计步单位。

### 43. 新增：每循环工具数可配置（用户补充）
一步=一次循环，但**每次循环最多可调用的工具数可配置，默认=4**。参数进 harness.yaml（max_tools_per_step: 4）。理由：防 LLM 一口气调 20 个工具把上下文刷爆；可配是因为不同任务节奏不同（快速侦察 vs 深度渗透）。与第 39 节撞限=停止执行形成两级刹车：工具数是单循环内刹车，步数是全局刹车。

## 44. 补遗七点（"跑起来之后最容易翻车"清单）
**并发**：①sqlite WAL+单写者原则（多写者撞 lock 崩溃，晚定返工 DAO）；②目标去重锁（探索图"正在处理"标志，防两 worker 同打一主机——失速计管重复劳动，此锁管重复并发）。

## 45. LLM 可靠性（防抖）五件套（用户补充进图）
**结构化强制**：每步输出走 schema 校验；失败→带错重试≤2→仍失败作废记审计（不悬死）。这是"每一步尽可能结构化"的执行机制。
**温度分档**：规划/工具调用低温 0~0.2；发散档（CTF 撞墙）才升温——稳定性与发散分场景。
**重复抑制**：同输入相似输出（连续提出同一规划）→失速计拉铃（输入侧=目标命令重复已在失速计，输出侧=规划重复是新补充的对称面）。
**幻觉防线**：事实必须锚黑板（raw_ref/小票），锚不上=臆测进不了报告——verify 占位期间唯一在岗的判真规则。
**超时兜底**：LLM 无响应→指数退避重试≤3→失败走异常收尾。网络饭也吃"降级收尾"这口锅。

## 47. 三大件施工答（用户问：断电续跑/可视化/输出裁判；并附"jev"释义）
**① 断电续跑 = run 状态水位线 + 黑板复建注意力包**：
- runs 表加 status(running|paused|interrupted|ended) + step_count 水位线——每次循环收尾即写入（事务同批落小票/双图/水位线）。
- 重启判定：status=running/interrupted 且 step_count<预算 → 从黑板重建注意力包（goal/plans/双图摘要/最近N条小票）继续跑；ended → 直接出报告。
- 关键性质：小票本来就是 append-only——黑板天生就是 checkpoint,主循环只做"复建"，不做"回放"。
**② 可视化 = 黑板 tail 服务，双形态共用一个出口**：
- audit 表 append-only 天生是事件流；起一个只读 tail 服务，CLI（直接 stdout）和 web（SSE/WebSocket 对话面板+输出框）**同源**——web 展示"详细对话过程"=角色气泡（主LLM/worker/LLMC）+ 小票摘要卡。
- 绝不让 UI 直接写黑板（只读 toll）；交互输入走 HITL 占位。
**③ 输出裁判 = verify 占位期的"冒烟裁判"**：
- L0（v0.1 就上）：PoC 冒烟复跑——claimed finding 的命令重放一次，退出码/输出模式匹配→verified，否则维持claimed。代码判零式，零 LLM。
- L1（后补）：nuclei/自制 checker 模板化断言。
- L2（真 verify）：PoC 深度复核（不误伤）+ 人工抽检走 HITL。
- 裁判结果落 findings.verify_state，LLMA 报告只取 verified+有 L0 记录的 claimed。
**"jev"释义**：猜测指 JSON——三件全可用 JSON 结构化支撑：黑板字段 JSON、事件流 JSONL、裁判断言 JSON Schema；若指别的（Yjs/Jupyter?）请纠正。

## 48. 输出裁判完整设计（用户追问：裁判怎么做，有什么好思路）
**核心洞见：靶场自带标准答案（oracle）**——lab 里的漏洞/flag 是预装的，ground truth 清单可进 profile.toml。裁判=比对预置清单，命中秒判——这是靶场阶段的天然优势，别家做真实目标裁判没有这张牌。
**裁判五道流水线（按成本从低到高逐级上）**：
- **R0 自证裁判**（零成本，全 finding 过筛）：证据充分性检查——raw_ref 里有没有直接证据（banner/响应包/dump 文件），还是只有推断链。纯代码判零，可过滤大半臆测。
- **R1 重放裁判**：只读操作的 PoC 冒烟复跑，退出码/输出模式匹配→verified。**写操作（有副作用）不可复跑**→转 R2/R3。
- **R2 双路径裁判**：两条独立路径（不同工具/不同 worker）同一结论→升级 verified。误报需"凑巧"一次，跨路径说谎成本高。
- **R3 反证裁判**：试图证明 NOT vulnerable（打失败/拿不到证据/逻辑不通）——捍卫型思维，反证失败即最强证实。
- **R4 oracle 裁判**（靶场专属）：findings 直接比对 profile.toml 预置 ground truth 表。
**裁决五字段（verdict schema）**：verify_state / 判定方法(rerun|dual-path|negative|oracle|llm-cross|manual) / 判据锚点(evidence_ref) / 置信度 / 判定时间。
**三条纪律**：
- 裁判先代码后 LLM：R0-R4 全代码可判；特殊情形才交 LLM 交叉复核——**必须 new session，不吃主 LLM 上下文**（"自己不信自己"）。
- 非幂等分支：写操作走"证据审查+反证"组合，永不 rerun。
- 报告出口把关：LLMA 只收 verified；claimed 且有 R0 记录的进"待验"段（明确标注，不上正典）。
