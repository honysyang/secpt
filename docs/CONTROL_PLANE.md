# secpt · 控制面设计

> 版本：v2（重写）。替代 v1 的"主控 + 黑板 + 并行"通用设想。
> 配套：`DESIGN.md`（组件与记忆总览）、`views/ARCH_3VIEWS.md`（三视角与 SOTA 对标）
> 适用：获得书面授权的渗透测试、红队演练、靶场与 CTF 评测。
>
> **v2 相对 v1 的变化**
> 1. 主控与子智能体统一为一个 runtime；主控必须能独立执行，不是纯调度器。
> 2. 增加教练（Mentor）与结果裁决（JEV）两个正交角色，并定义其权力边界。
> 3. 失败从"布尔值"改为"自报 × 判据"矩阵，重试拆成四种。
> 4. 记忆与存储分离：记忆是视图，存储是事件账本 + 证据库。
> 5. 补充 v1 缺失的四件事：立项契约、评测体系、模型降级、跨客户隔离。

## 0. 定位与边界

**做什么**：接收一个安全任务（CTF / 漏洞扫描 / 综合应用 / 渗透），无人值守自动执行，产出**带证据链的交付物**。任务可能持续数小时到数天。

**关键约束**（决定了后面所有设计）：

| 约束 | 后果 |
|---|---|
| 长任务 | 必须可恢复：状态外置、断点续跑、幂等 |
| 主控能独立执行 | 主控不能是纯调度器，必须是 full agent |
| 多智能体按需 | 需要可计算的扇出判据，不能靠模型自觉 |
| 交付甲方 | 证据链、可复现、误报可控、人工签发 |

**不做什么**：

- 不做无授权的任何测试；不做"自动发现目标"（目标必须由人给）。
- 不做多租户 SaaS（当前形态是单机/小队工具）。
- 不在 v1 做跨战役技能自进化（没有数据量支撑，会污染技能库）。

## 1. 总图与五条硬结论

```
                    ┌─────────────────────────────────────┐
   用户输入 ───────▶│ 应用层：Mission 立项 / 报告 / 交付    │
                    └──────────────┬──────────────────────┘
                                   │ MissionSpec ↓  Deliverable ↑
                    ┌──────────────┴──────────────────────┐
                    │ 引擎：回合驱动 · 任务图 · 预算 · 租约  │
                    │      动作网关 · 检查点 · 事件总线      │
                    └──────────────┬──────────────────────┘
                       RunContext ↓│↑ Decision（纯数据）
                    ┌──────────────┴──────────────────────┐
                    │ 核心层（主控/子智能体，同一循环）      │
                    │ 上下文组装 · 决策 · 委派 · 反思        │
                    └───┬──────────────────────────┬──────┘
                        │ 轨迹/证据                 │ 建议/否决/裁决
                    ┌───▼──────────┐        ┌──────▼──────────┐
                    │ Mentor 教练   │        │ JEV 结果裁决     │
                    │ 管过程        │        │ 管结论           │
                    └──────────────┘        └─────────────────┘
                    ┌─────────────────────────────────────┐
                    │ 模型层：路由 / 结构化输出 / 缓存 / 成本 │
                    └──────────────┬──────────────────────┘
                    ┌──────────────┴──────────────────────┐
                    │ 基础设施：一次性执行容器 · 网络 · 存储  │
                    └─────────────────────────────────────┘
```

**五条硬结论**

1. **一个 Runtime，两个角色。** 主控与子智能体跑同一套循环，差异只有四个字段（作用域、可否派发、预算权、汇报对象）。这保证主控不会退化成"只会拆任务不会干活"。
2. **判定归教练，处置归父。** 教练只回答"这是不是失败 / 该不该继续"，父只回答"那怎么办"。任何一层都不允许自判自决。
3. **过程归 Mentor，结论归 JEV。** 两个角色正交，不抢活。教练只能收紧，不能放行。
4. **状态只存引擎，记忆只是视图。** 智能体无状态；工作记忆每轮渲染；因此 resume / replay / 评测 / 报告四个能力共用一份数据。
5. **机制开放，底线关闭。** 策略可由人改（范围、风险档、审批规则），但审计、越界判定、不可逆动作默认值不可改。

## 2. 分层架构

| 层 | 职责 | 关键模块 | 契约 | 做错的后果 |
|---|---|---|---|---|
| **应用层** | 立项、报告、交付 | Mission 接入、报告渲染、监控/续跑、对外集成 | `MissionSpec` → `Deliverable` | 交付物结构漂移 |
| **引擎** | 何时跑、跑谁、能否跑、存哪 | 回合驱动、任务图、预算、租约、动作网关、检查点、事件总线 | `step()` | 状态不一致、重复执行 |
| **核心层** | 想什么、做什么、要不要拆 | 上下文组装、决策、委派、反思、记忆检索、工具 schema | `decide(RunContext) → Decision` | 上下文腐化、扇出失控 |
| **模型层** | 推理后端 | 路由、重试降级、结构化输出、前缀缓存、成本归因 | `complete(PromptBundle)` | 成本失控、解析失败 |
| **基础设施** | 副作用执行与持久化 | 一次性容器、网络/跳板、存储、密钥、追踪 | `execute/load/store` | 隔离失效、证据丢失 |

**三条跨层铁律**

1. 状态只存在引擎；核心层、模型层无状态。
2. 副作用只走动作网关；模型调用只走模型层 wrapper。两个收口点分别承担去重幂等与成本缓存。
3. 依赖单向向下，反向只走事件。下层不得回调上层业务逻辑。

## 3. 运行模型：一个 Runtime，两个角色

### 3.1 主控与子智能体的四个差异

| 字段 | 主控 | 子智能体 |
|---|---|---|
| `scope` | mission 全域 | 单个任务切片 |
| `can_spawn` | true | false（或限深 1） |
| `budget_authority` | 可分配 | 只能消耗 |
| `report_to` | 人 / 引擎 | 父 |

其余完全相同：同一套 ReAct 循环、同一套工具 schema、同一套技能注入。

**为什么不做"调度器 + 执行器"两套**：

- 主控能独立干活，才能**亲自复核子智能体的可疑结论**（发一条 curl 验证"已 RCE"）。纯调度器只能相信报告。
- 只维护一套循环，能力自然对齐，不会退化。
- 递归结构天然支持子再拆，但建议限深 1~2 层。

### 3.2 Mode S / Mode T

**模式不是任务开始时选的，是每个子目标决策时选的。** 一个 mission 可以全程 S，中途进 T，再回 S。

| 模式 | 形态 | 适用 |
|---|---|---|
| **S（单干）** | 主控自己 ReAct | 无独立支线、步数少、上下文可控 |
| **T（带队）** | 主控仍走主线，支线派出去 | 有 ≥2 个独立支线，或支线产生大量噪音输出 |

**扇出判据（必须可计算，不能靠模型自觉）**——同时满足才扇出：

1. 存在 ≥2 个**互相独立**的子任务（无数据依赖）；
2. 每个子任务预计 ≥ 8~10 步（低于此协调成本大于收益）；
3. 子任务需要**不同的上下文**，或子任务墙钟远大于等待成本。

**强制不扇出**：有依赖链、共享会话/凭证、子任务太短、剩余预算不足、**上下文余量 > 70%**（此时扇出是卸载上下文，不是提速）。

**实现分三层**：LLM 提议 → 规则校验独立性 → 预算层截断到付得起的数量。

### 3.3 超级步

主循环按批推进，不按动作推进。

```
superstep(t):
  1. OBSERVE   收集上一批结果 + 异步事件（后台任务完成 / 告警 / 人工指令）
  2. REVIEW    Mentor 按梯度介入；失败按矩阵判定
  3. MERGE     结果写黑板；冲突检测；线索入图；证据挂 ID
  4. REPLAN    触发条件成立则局部重规划
  5. SELECT    ready 集合按优先级取 Top-K（K = 并发上限）
  6. DISPATCH  编译 briefing、发租约、起 worker
  7. CHARGE    预算结算 + 检查点落盘
```

**按批的理由**：按步推进时一个慢任务阻塞全部分支；按批推进时同批互不等待。**代价**：批内看不到彼此产出，因此必须由 ready 集合保证批内互不依赖。

### 3.4 结束条件（立项时就固化，运行时只判定不讨论）

1. **达成**：所有 must-have 验收项都有证据。
2. **预算耗尽**：token / 时间 / 命令数 / 费用任一触顶。
3. **平台期**：连续 N 超级步无新事实、无 ready 高价值任务、重规划无实质变化。
4. **风险熔断**：网关拦截升级、人工叫停、蜜罐告警。
5. **人工收口**。

缺 2/3/4，长任务会无限打转——这比模型能力不足更常见。

## 4. 计划：类型化 DAG + 滚动时域

### 4.1 Task 结构

```jsonc
{
  "id": "t-0042",
  "type": "recon.smb_enum",              // 决定技能注入与工具集
  "goal": "枚举 10.0.0.5:445 的 SMB 版本与共享",
  "parent": "t-0010",
  "deps": ["t-0031"],                    // 硬依赖
  "preconditions": [                     // 软依赖，由黑板事实判定
    {"kind": "clue", "match": {"host": "10.0.0.5", "port": 445, "state": "open"}}
  ],
  "success_criteria": [                  // 指向证据类型，不是形容词
    {"evidence": "smb.version", "required": true},
    {"evidence": "smb.shares",  "required": false}
  ],
  "abort_criteria": ["3 次 TCP 握手超时", "触发账户锁定告警"],
  "scope_slice": {"hosts": ["10.0.0.5"], "ports": [445], "noise": "low"},
  "allowed_tools": ["nmap_smb", "smbclient"],
  "budget": {"steps": 12, "seconds": 180, "tokens": 40000, "risk": "low"},
  "priority": 0.72,
  "state": "ready",                      // pending|ready|running|done|failed|blocked|superseded
  "lease": {"owner": "w-3", "expires": "..."},
  "attempt": 2,
  "tried": ["a3f1…", "9c02…"],           // 已试战术指纹，跨尝试继承
  "lineage": {"supersedes": null, "superseded_by": []}
}
```

两个承重设计：

- **`success_criteria` 指向证据类型**。这解决了长任务最难的"什么时候算完"。
- **`preconditions` 让"补前置"变成自动动作**（缺凭证 → 插入 `credential.obtain` 子任务），而不是让模型自由发挥。

### 4.2 分层规划 + 滚动时域

- **深度 0**：抽象节点（`compromise.domain_admin`）
- **深度 1**：方法选择（HTN method，可并列）
- **深度 2**：可执行任务，只展开当前 + 下一个超级步
- 更深的保持抽象，等前置任务的观察结果出来再展开

收益：计划规模从 O(全部) 降到 O(窗口)，避免在信息不足时臆造 40 步。

### 4.3 重规划触发

| 触发 | 动作 |
|---|---|
| 新线索使某任务前置成立 | pending → ready（最常见的正向触发） |
| 发现新攻击面（网段/主机/服务） | 增量扩展 DAG，按资产分片扇出 |
| 失败归因为 Plan | 插入前置任务 或 拆分任务 |
| 失败归因为 Env/Tool | 原地重试，换参数/换工具（≤2） |
| 假设被两条证据矛盾 | 生成 `resolve` 任务，不静默覆盖 |
| 连续 N 步无新线索 | 升级：换分支 / 提噪音档 / 上报 |
| 预算超阈值 | 收窄到 must-have，停掉探索型任务 |

**降级模式（探索步）**：ready 为空且无高价值任务时，允许 1~2 步纯 ReAct 探索，唯一目的是产出新线索。必须标注 `explore=true` 且有独立小预算。

## 5. 团队协作

### 5.1 拓扑：三通道星形

```
              ┌──────────┐
   Human ────▶│  Engine  │◀──── 事件
              └────┬─────┘
       委托下行    │    ▲ 结果上行
                   ▼    │
              ┌──────────┐
              │   Core   │
              └────┬─────┘
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Worker-1   Worker-2   Worker-3      ← 互相之间：无连接
```

| 通道 | 方向 | 形态 | 频率 |
|---|---|---|---|
| 委托 | 父 → 子 | `WorkerRequest`（一次，不可变） | 每任务 1 次 |
| 结果 | 子 → 父 | `WorkerResult`（一次，结构化） | 每任务 1 次 |
| 状态 | 任意 ↔ 黑板 | 读投影 / 提交事实 | 每步 |
| 心跳 | 子 → 引擎 | 进度事件（不发给父） | 周期 |

**禁止**：子智能体互连、子智能体改全局状态、长连接会话。

> **协作问题的 90% 应在调度层解决，不在通信层解决。** 两个 worker 需要"商量谁先打"时，正确做法是用租约/干扰图排开，不是开对话通道。一旦开始设计 agent 间对话协议，基本可以确定任务拆分或调度出了错。

### 5.2 五种协作模式

| 模式 | 形态 | 用在哪 |
|---|---|---|
| 接力 | A 完成 → 结果喂 B | 依赖链（拿凭证 → 横向） |
| 扇出/汇聚 | 拆 N → 并行 → 汇总 | 独立子任务 |
| 监督 | 旁路 Mentor，梯度介入 | 全程 |
| 升级 | 失败 → 换强模型/加预算 | 重要分支 |
| 竞争 | 同任务两 worker 不同策略，先成者胜 | **v1 不做**（成本翻倍） |

### 5.3 单写者黑板

```
Worker 提交 intent（clue / finding / evidence）
        ↓
Engine 校验：schema、证据引用、冲突检测
        ↓
Engine 写入（唯一写者）
        ↓
其他 agent 通过投影读取
```

**只有引擎写。** 因此不需要 agent 级锁，并发问题退化为"提交顺序"，由回合边界保证。

冲突处理：同一 key 两个值 → 不覆盖，生成 contradiction 节点，派 `resolve` 任务。优先级：**原始回显 > 工具解析 > 模型推断**。

读取是投影：

| 读者 | 拿到什么 |
|---|---|
| Worker | 与任务相关的线索切片（按图距离 Top-K） |
| Core | mission 摘要 + 待办 + 已确认事实 |
| Mentor | 指标 + 轨迹摘要（不含执行者自述） |
| JEV | 单个 Finding 的**全量**证据包 |

### 5.4 状态同步：冻结简报 + 拉取游标

```
dispatch 时：briefing 冻结（快照版本 + clue_cursor = 1024）
运行中：worker 可主动 pull("id > 1024 且匹配 port:445")
```

用**拉**不用**推**：推会打断推理节奏且破坏可复现；拉是幂等、单调、可重放的。

**父不等子。** 父交出去就干别的，子完成时通过事件唤醒。超时由引擎按租约判定后通知父。父子之间不存在阻塞等待。

### 5.5 契约

```jsonc
// WorkerRequest
{
  "task_id": "t-0042",
  "goal": "...",
  "success_criteria": [...], "abort_criteria": [...],
  "scope_slice": {...}, "allowed_tools": ["..."],
  "budget": {"steps": 12, "seconds": 180, "tokens": 40000, "risk": "low"},
  "briefing": {
    "relevant_clues": [...],        // 图邻近度 Top-K
    "applicable_skills": [...],     // 按 task_type 精确匹配
    "applicable_lessons": [...],    // 按 (task_type, target_fp, failure_class)
    "known_state": {...},
    "failed_attempts": [...],       // 只给"结论 + 已试指纹"，不给推理过程
    "untrusted_data": [...]         // 目标回显，结构化隔离区
  },
  "clue_cursor": 1024,
  "deadline": "...", "lease_id": "..."
}

// WorkerResult
{
  "status": "done|partial|failed|blocked|needs_help",
  "findings": [...], "clues": [...], "evidence_refs": [...],
  "tried": ["a3f1…"],               // 回写，供下次继承
  "confidence": 0.7,
  "cost": {"tokens": 0, "seconds": 0, "calls": 0},
  "proposals": [ /* Task[]，不能直接写 DAG */ ],
  "failure": {"class": "Env|Tool|Model|Plan|AuthZ|Deception", "detail": "...", "evidence_ref": "..."}
}
```

**让 worker 自报失败类别**，教练只做校验与升级——否则每次失败都要重读全部轨迹，成本爆炸。

## 6. 失败判定与恢复

### 6.1 四个层次的"失败"（F0~F3）

混着说就会做出"重试五次还在同一个死路上"的系统。

| 层 | 定义 | 时间尺度 | 后果 |
|---|---|---|---|
| **F0 动作** | 工具报错、超时、连接拒绝 | 秒 | 换参数继续，**不算失败** |
| **F1 进展** | 连续 k 步无新事实、动作指纹重复 | 分钟 | 换战术（同一尝试内） |
| **F2 目标** | 一次尝试未在预算内满足判据 | 十分钟 | 计入尝试次数 |
| **F3 分支** | 假设被证伪（判断错，不是执行错） | 小时 | **不重试**，去验别的假设 |

第四行最容易搞错：假设被证伪了系统还在重试，因为归因写成了"执行失败"。**先分清"假设错了"还是"假设没打成"。**

### 6.2 判定矩阵：自报 × 判据

| 自报 | 客观判据 | 真实判定 | 处理 |
|---|---|---|---|
| done | 满足 | 真成功 | 接受 |
| **done** | **不满足** | **虚报成功** ⚠️ | 不重试，降级 partial / 交 JEV |
| failed | 不满足 | 真失败 | 归因后选重试方式 |
| failed | 满足 | 误报失败 | 接受结果，标记该 worker 不可靠 |
| blocked | — | 外部拦住 | 不重试，回主控改计划 |
| partial | 部分满足 | 部分成功 | 保留已得，未达成部分拆出重派 |
| needs_help | — | 能力不足 | 升级（换强模型/加预算/父接管），不是重试 |

**状态由 worker 自报，判决由引擎按证据做。** 统计上最常见的不是 failed，而是"done 但判据不满足"——模型会把"我做了"当成"我做成了"。

### 6.3 重试的四种形态

```
retry（同战术重试）      ≤ 2 次   仅限 Env/Tool 瞬时原因
rework（换战术重做）     ≤ 3 次   换维度：参数/工具/协议/入口/身份/时间窗
re-decompose（重构）     不限次   任务本身错了，拆分或替换。需 Mentor 批
abandon（弃分支）        终态     假设被证伪
```

"重试 3 次"这种粗暴上限会把不该重试的和不该放弃的混在一起。

**战术维度固定 8 个**，防止模型自由发挥：`换参数 / 换工具 / 换协议变体 / 换入口点 / 换身份 / 换时间窗 / 补前置 / 放弃分支`。

### 6.4 重启语义

**重置执行状态，不重置认知状态。**

| 保留 | 重置 |
|---|---|
| 已收集线索 | 任务状态 → ready |
| 已落库证据 | worker 上下文（新派时） |
| `tried` 指纹 | 租约 |
| 失败摘要 | 步数计数 |
| 任务血缘（lineage） | — |

线索和证据绝不因重启而丢——它们是资产，不是本次尝试的副产品。`tried` 必须继承，否则新 worker 重走老路。

**谁决定**：Mentor 判"是不是任务失败"，父决定"怎么重新开始"。

派的六个选项：

| 诊断 | 处置 |
|---|---|
| 判据无法判定 | 修订 `success_criteria`，重派 |
| 粒度太粗 | 拆分成 2~N 个子任务 |
| 前置缺失 | 插入前置任务，本任务延后 |
| 权限/工具不足 | 扩权申请（网关或人可拦） |
| 假设被证伪 | 弃分支，转其他假设 |
| 环境问题 | 退避后重排（不消耗尝试次数） |

**原地 vs 新派**的判据不是"失败了多久"，而是**这次失败有没有改变"该怎么办"**：

```
失败改变了战术  → 新派（新上下文，保留线索/tried，丢弃推理过程）
失败没改变战术  → 原地（保留现场：会话、响应细节）
步数 > 60%      → 新派（无论归因）
```

新派时 briefing 带 `failed_attempts`：**结论 + 已试指纹**，不带推理链。

### 6.5 重启不能续命

重启消耗的是**同一个父任务的预算**，不是新预算。

```
父任务预算 30k
  ├ 尝试 1: 12k（失败）
  ├ 重启 1: 10k（失败）
  ├ 重启 2: 8k  ← 见底
  └ 再重启 → 必须向 mission 池申请，Mentor 批
```

每条重启留结构化记录，这是复盘的核心原料：

```jsonc
{ "restart_id": "r-007", "task": "t-0042",
  "diagnosis": "hypothesis_refuted",
  "changed": {"split_into": ["t-0051", "t-0052"]},
  "budget_before": 12000, "budget_after": 6000,
  "decided_by": "core", "confirmed_by": "mentor" }
```

### 6.6 防虚报：证据溯源

```
每个 evidence_ref 必须满足：
  1. 存在对应的 tool_call 记录
  2. 输入参数与该 tool_call 一致
  3. 输出哈希匹配
  4. 时间戳在该 worker 的租约窗口内
```

任一不满足 → `invalid_claim`，既不算失败也不接受，单独记账。

**几条代码挡住最严重的一类问题**，且模型一旦知道会被核验就很少编。

### 6.7 任务图治理

重启会加节点。跑几天后不治理，图会变成几百个死节点的坟场。

1. 旧任务不删，标 `superseded`，指向新任务（lineage）。
2. 只有 `ready` 参与调度，`superseded`/`failed` 不参与优先级计算。
3. 同源链路压缩：连续 supersede 合并为一条，只保留分叉点。

## 7. 教练 Mentor

### 7.1 定位

**第三人称视角的过程教练。** 不是评审员（评结果），是教练（管过程）。核心价值不是"多一双眼睛"，而是：

- 它看的是**漂移和证据**，不是执行者的自我陈述；
- 它能在**失败之前**介入（等失败发生，沉没成本已经付了）。

### 7.2 五级介入梯度（I1~I5）

| 级 | 形态 | 触发 | 能否被忽略 |
|---|---|---|---|
| **I1 静默** | 什么都不说 | **默认** | — |
| **I2 记录** | 写黑板，不打扰 | 轻微可疑（供复盘） | 可以 |
| **I3 提醒** | 下一轮注入一条提示 | 漂移指标偏移 | 可以，但计数 |
| **I4 否决** | 阻断 Decision，要求替代 | 关口 / 提醒被忽略 | **不可** |
| **I5 升级** | 换模型 / 通知人 / 熔断 | 否决被绕过 / 高风险 | 不可 |

**I1 必须是最高频输出。** 大多数步骤本来就没错，说话就是噪音。

I2 与 I3 的区别值得保留：没有 I2，教练只剩"闭嘴"和"打断"两档，会滥用打断。

### 7.3 提醒必须有牙齿

```
同一主题的提醒被忽略 2 次 → 自动升级为 I4 否决
否决被绕过（force）      → I5 升级，写入审计
同一主题不重复第 3 次    → 要么升级，要么撤回
```

第三条同样重要：教练反复说"你在原地打转"，说三次就没人听了。

### 7.4 关口（必须过审）

| 决策 | 何时强制 |
|---|---|
| **计划评审** | 每次计划（或重规划）生成后，**执行前** |
| **扇出** | 每次 spawn |
| **收口** | 每次 finish（过早收工是最常见的失败） |
| **弃分支** | 每次 abandon（沉没成本重灾区） |
| 重启 | 每次 re-decompose |
| 阶段切换 | 语义变了，之前判断可能整体失效 |
| continue | 仅信号触发 |
| 普通工具调用 | **不审**（过审就是审批流，必死） |

### 7.5 计划评审清单

结构问题用代码查，语义问题才用模型。

| 检查项 | 谁查 | 判据 |
|---|---|---|
| 判据可判定性 | **代码** | 每个 criteria 指向 evidence 类型 |
| 前置闭合性 | **代码** | 没有"要凭证但无获取任务" |
| 终止条件 | **代码** | 达成/预算/平台期三件套齐全 |
| 范围一致性 | **代码** | 计划动作都在授权范围内 |
| 并行合法性 | **代码** | 并行任务不共享会话/凭证/告警域 |
| 粒度 | **代码** | 无预计 > 50 步的巨型任务 |
| 预算匹配 | 代码 + 模型 | 分布与任务价值匹配 |
| 风险前置 | **模型** | 高危动作没排在信息不足阶段 |

七项里六项是代码，既便宜又具体，还能挡住"教练只会说套话"的通病。

### 7.6 漂移指标（替代"3 次偏离"这类滞后阈值）

全部可算，不用问模型：

| 指标 | 含义 |
|---|---|
| 计划改写频率 | 规划质量差，不是执行问题 |
| 同一任务重启次数 | 沉没成本，父在硬撑 |
| 新增任务数 / 计划任务数 | 计划无效，边打边编 |
| 预算消耗斜率 vs 预期 | 估算系统性偏低 |
| `tried` 增长速度 | 在试错而非推理 |

**教练不该等失败，应该等漂移。**

### 7.7 否决语义

```jsonc
{
  "verdict": "approve | veto",
  "target": "spawn#17",
  "reason": "三个子任务共用同一会话，并行会互踢",
  "alternative": "串行；或为每个子任务导出独立 cookie",
  "unlock_condition": "若确认三者使用独立 cookie jar，则放行",
  "confidence": 0.8,
  "evidence_refs": ["ev-0231"]
}
```

三条硬性质：

1. **只有否决权，没有发起权。** 不能说"你应该去打 10.0.0.7"。
2. **否决必须带可执行替代**，否则降级为 `objection` 并放行。无替代的否决等于无限次重开。
3. **权限单向：只能收紧，不能放开。** 不能放行越界动作、不能豁免高危拦截——否则它就成了绕过网关的最短路径。

`unlock_condition` 让否决可证伪，也省掉一轮往返。

### 7.8 独立性与成本

| 手段 | 成本 | 必要性 |
|---|---|---|
| 独立上下文（只喂黑板） | 免费 | 必需 |
| 不读执行者自述 | 免费 | 必需 |
| 独立预算 | 免费 | 必需 |
| 不同 system prompt | 免费 | 必需 |
| 不同模型 | 中等 | 强烈建议 |
| 喂"历史同类失败案例"而非"当前任务难度" | 便宜 | 有效，抗同源误判 |

**成本线：调用次数与阶段数成正比，与步数无关。**

| 形态 | 1500 步任务 | 占比 |
|---|---|---|
| 按阶段（评审+心跳+信号+关口） | ~150 次 ≈ 120 万 token | **2.7%** |
| 按步 | 1500 次 ≈ 1200 万 | 27% |

节奏：计划评审每次计划修订 1 次；心跳每 30 步或阶段切换；信号触发；关口。

### 7.9 边界

- **不写记忆。** 判断可作复盘素材，但不能直接沉淀成技能（否则用今天的偏见训练明天）。
- **Mode S 不激活**（三步任务配教练是浪费）。
- **必须被评核**：记录每次 veto 的 `unlock_condition` 事后是否成立、approve 是否翻车、veto 造成的停滞时长。没有闭环，两周内退化成噪音。

## 8. 结果裁决 JEV

### 8.1 与 Mentor 的分工

| | Mentor | JEV |
|---|---|---|
| 管什么 | **过程**：该不该继续/转向/拆 | **结论**：这条成立吗 |
| 输入 | 漂移指标、轨迹摘要 | **全量**证据包 |
| 输出 | approve / veto（带替代） | confirmed / suspected / false_positive |
| 节奏 | 关口 + 信号 | 每个 Finding 一次 |
| 权力 | 否决（只能收紧） | 裁决 + **要求补证** |

**过程归教练，结论归裁决。** 两者正交，不抢活。

### 8.2 反证优先

整条执行链都在找**支持**"有洞"的证据——执行者有动机，上下文也在往这个方向累积。如果 JEV 也只问"成立吗"，它必然退化成盖章机。

给它的任务必须是反的：

> **"假设这条结论是误报，最可能的原因是什么？"排除不了，就不要判 confirmed。**

它能抓住的典型假阳性：

- 回显里出现 payload，但被 HTML 转义（不是注入）
- 401 变 200，但那是错误页（不是越权）
- 命令返回字符串，但来自本地 mock（不是 RCE）
- 版本号匹配 CVE，但编译选项禁用该功能（不可利用）

### 8.3 裁决 schema

```jsonc
{
  "finding_id": "f-0012",
  "claim": "10.0.0.5:8080 存在 SQL 注入（id 参数，布尔盲注）",
  "evidence_refs": ["ev-0231", "ev-0237"],
  "reproduce": "curl -s '.../item?id=1%20AND%201=1' | grep '商品'",
  "falsify_if": ["参数化查询生效", "差异来自缓存而非数据库"],
  "counter_evidence": ["ev-0240"],
  "verdict": "confirmed | suspected | false_positive",
  "verdict_by": "jev-v0 | human",
  "unlock": "若提供盲注时间差 ≥ 3s 的稳定复现，则升为 confirmed"
}
```

`falsify_if` 与 `counter_evidence` 是"反证优先"在数据结构上的落点。**v0 不写这两个字段，将来所有裁决都会退化成"再看一眼觉得像"**，因为反证信息根本没人采集。

### 8.4 全量证据

**证据由引擎在动作执行时全量落盘，执行者只能引用、不能筛选。**

如果证据是执行者"提交"的，它就能只提交有利的部分，JEV 看到的世界是被润色过的，裁决成了盖章。

### 8.5 补证

JEV 可以要求 Core 补一次验证（"我需要看到响应体里确实回显了 id"）。这是它比 Mentor 多的一项权力。

**上限：每个 Finding 最多要求 2 次**，第 3 次按现有证据定级并标注"证据不足"。否则会变成"再验一次"的无限循环。

### 8.6 校准

用靶场和已知 CVE 环境做 ground truth，测 JEV 的 precision / recall。

**没有校准集的裁决者，可信度不会高于它替代的人工判断**——那只是把误报换了个地方产生。

## 9. 记忆与存储

**记忆是取用的方式，存储是落盘的方式。** 同一份存储可以有不同的记忆视图。混在一起就会做成"一个向量库什么都往里塞"。

### 9.1 一真源，四投影

```
┌ S0 事件账本（append-only，唯一真源）──────────────────┐
│ 决策、动作、结果摘要、成本、人工指令、重启记录           │
└────────────┬─────────────────────────────────────────┘
             │ 投影（可重建）
   ┌─────────┼──────────┬──────────┬─────────────┐
   ▼         ▼          ▼          ▼             ▼
 任务图    线索图      审计视图    报告素材      评测集
   ▲
   │ 引用
┌──┴ S1 证据库（内容寻址，不可变）──────────────────────┐
│ 原始回显、截图、pcap、导出文件                          │
└──────────────────────────────────────────────────────┘

┌ S3 资产库（版本化）──┐   ┌ S4 索引（可重建）──┐
│ 工具/角色/技能/经验/知识 │   │ FTS / 向量 / 图   │
└─────────────────────┘   └──────────────────┘
```

**推论：只有 S0 和 S1 不可重建。** 备份这两样，其余全部可重算。

### 9.2 存储分层

| 层 | 内容 | 形态 | 体量 | 可重建 |
|---|---|---|---|---|
| S0 账本 | 事件 | SQLite(WAL) / JSONL 分段 | MB/天 | ❌ |
| S1 证据 | 原始输出 | 内容寻址文件 | GB | ❌ |
| S2 状态 | 任务图、线索图 | SQLite 表 | 小 | ✅ |
| S3 资产 | 技能/经验/知识 | 文件 + DB | MB | 部分 |
| S4 索引 | 全文/向量/图 | 独立索引 | 中 | ✅ |

**为什么不是一个数据库**：证据是 GB 级二进制，塞进 SQLite 会拖垮主库；事件是 append-only 不需要事务；索引重建频繁，独立才不会锁主库。

### 9.3 三种记忆

| 记忆 | 本质 | 实现 | 写入时机 | 淘汰 |
|---|---|---|---|---|
| **工作记忆** | **视图，不存储** | `render(state, task) → prompt 片段` | 每步现算 | 随轮次丢弃 |
| **短期记忆** | 当前 mission 轨迹 | S0 分区 + S2 投影 + 分段摘要 | 运行时自动 | mission 结束归档 |
| **长期记忆** | 跨 mission 资产 | S3 | 复盘 + 门控 | TTL + 置信衰减 |

三条规则：

1. **工作记忆必须渲染出来**，不能累积。这一条决定几天任务能不能跑。
2. **短期记忆分层摘要**：每 20 步压一个 segment，检索先命中 segment 再回查原始事件。**segment 是记忆的基本单元，不是单条事件。**
3. **长期记忆只放可复用结论**，不放过程。

### 9.4 证据：内容寻址

```
id   = "ev-" + sha256(content)[:16]
meta = { tool_call_id, task_id, ts, target, size, mime }
body = 原始字节（大文件单独落地，meta 存引用）
```

- **可校验**：甲方验报告时哈希对得上，比"我们没改"有说服力。
- **天然去重**：同一回显被两任务抓到只存一份。
- **不可变**：只能追加和标记删除，这是审计前提。

### 9.5 索引选择

| 需求 | 选择 | 理由 |
|---|---|---|
| 日志/证据全文 | SQLite FTS5 | 够用，零运维 |
| 经验相似度 | 小向量库 | 只有经验需要；技能按 `task_type` 精确匹配 |
| 攻击图查询 | **SQLite 递归 CTE** | 几万节点秒级 |

**攻击图不要上 Neo4j。** 一个 mission 最多几万节点，专用图库换来的是运维负担和一致性难题。

### 9.6 账本放什么、不放什么

| 放 | 不放 |
|---|---|
| 决策（Decision JSON） | prompt 全文 |
| 动作（工具名 + 参数摘要 + 指纹） | 原始工具输出（进 S1） |
| 结果状态 + 归因 | 完整推理链 |
| 成本 | 二进制 |
| 人工指令、重启记录、否决记录 | 重复观测副本 |

**要能复现 prompt，但不存 prompt。** 存生成参数：

```jsonc
{ "prompt_ref": {
    "template_version": "core@12",
    "asset_snapshot": "as-20261025-03",
    "state_seq": 18422,
    "token_budget": 32000 } }
```

### 9.7 崩溃恢复

```
启动
 → 加载最后一个快照（每 N 事件一份）
 → 重放快照之后的事件（目标 < 1 万条，秒级）
 → 校验租约：过期任务回 ready
 → 校验在途进程：job registry 中存活的，重连或接管
 → 继续调度
```

三个必要条件：事件带单调 `seq`；带 `idem_key` 去重；快照定期做（否则几天后重放要几十分钟）。

### 9.8 表结构

```sql
mission(id, objective, env_class, budget_total, roe_json,
        asset_snapshot, created_at, status)

event(seq INTEGER PK, mission_id, ts, type, actor,
      payload_json, idem_key UNIQUE)

task(id, mission_id, type, goal, deps_json, criteria_json,
     state, budget_json, lease_json, attempt, lineage_json)

clue(id, mission_id, kind, key, value, evidence_id,
     confidence, source_task, ts)

evidence(id PK, sha256, path, size, mime, tool_call_id, task_id, ts)

finding(id, mission_id, claim, evidence_ids_json,
        verdict, verdict_by, falsify_if_json, counter_evidence_json)

asset(kind, id, version, body_json, scope, ttl_days,
      confidence, verified_count, source_refs_json)
```

### 9.9 mission 目录

```
mission/

  ├ events.jsonl      # S0，一行一事件，seq 单调
  ├ state.sqlite      # S2 投影（可从 events 重建）
  ├ evidence/         # S1，按 sha256 命名
  ├ snapshot.json     # 每 200 事件一份
  └ report.md         # 从 S2 渲染
```

## 10. 资产：工具 / 角色 / 技能 / 经验 / 知识

### 10.1 五元对照

| | 本质 | 谁写 | 检索 | 生命周期 | 信任级 |
|---|---|---|---|---|---|
| **工具** | 可执行能力 | 人注册 | 精确名字 | 版本化，稳定 | 最高 |
| **角色** | 装配产物 | 人 + 系统提议 | 按任务类型 | 慢变 | 高 |
| **技能** | 程序性知识 | 复盘 + 门控 | `task_type` 精确 | 慢变，需验证 | 中 |
| **经验** | 情景记录 | **运行时自动** | 相似度 | 快变，会过期 | 低-中 |
| **知识** | 声明性事实 | 人 / 外部源 | key 精确 | 中速，TTL | 中-高 |

### 10.2 四条原则

**1. 能力原语 → 装配 → 使用，是三层**

```
知识（前提事实）
   ↓ 被引用
技能（用工具的程序）  ← 工具（原子能力）
   ↓ 被组合
角色（prompt + 工具子集 + 技能子集 + 判据 + 模型档）
   ↓ 被执行
经验（这个角色的实际表现）
```

角色是**装配产物**，不是花名册。维护"角色库"会角色爆炸。做法：维护能力标签，角色由 `任务类型 + 约束` 过滤；常见组合固化成 preset（web-injection / ad-enum / privesc），未覆盖的走动态装配。**preset 是糖，不是架构。**

**2. 经验 ≠ 技能，中间有门控**

```
经验 →（≥2 独立案例 或 人工确认）→ 技能候选 →（跨目标验证）→ 技能
```

一次侥幸成功直接写成"最佳实践"，会污染此后所有任务，而且看起来很有道理。

**3. 知识必须分域（合规红线）**

```jsonc
{ "scope": "global" | "client:<id>" | "mission:<id>" }
```

**目标事实（资产、指纹、凭证、路径）属于 mission 状态，不属于知识库。** 混进去会导致跨客户污染——这不是技术问题，是事故。

**4. 只有"经验"可以无门控自动写**

| 资产 | 自动写 | 门控 |
|---|---|---|
| 经验 | ✅ | 无（带 TTL 和置信度） |
| 技能 | ⚠️ 只到候选 | ≥2 独立案例 / 人确认 |
| 知识 | ⚠️ 外部同步 | 来源校验 |
| 角色 | ⚠️ 只到提议 | 人确认 |
| 工具 | ❌ | 人注册 |

唯一能自动写的是"发生了什么"，"该怎么办"必须过闸。**事实错了可以改，规则错了会自我强化。**

### 10.3 Schema

```jsonc
// 工具：让程序可消费，不只是让模型读
{ "name": "smb_enum", "version": "2.1", "schema": {...},
  "side_effect": "read", "risk_tier": "low",
  "cost": {"seconds": 30, "calls": 1},
  "requires": ["port:445:open"],       // 喂"补前置"
  "produces_evidence": true,
  "output_parser": "smb_v2" }          // 结构化解析，别让模型读原文

// 技能：可执行、可验证、可失效
{ "id": "sk-smb-relay",
  "trigger": {"task_type": "exploit.smb", "target_class": "windows_server"},
  "preconditions": ["smb_signing:disabled"],
  "steps": [...], "success_check": "evidence:ntlm_relay_success",
  "pitfalls": ["签名开启时静默失败"],
  "confidence": 0.72, "verified_count": 5,
  "last_verified": "2026-09-12", "ttl_days": 180,
  "source_refs": ["ep-0031", "ep-0044"] }

// 经验：检索用，不直接进提示词全文
{ "id": "ep-0044", "mission": "m-2026-1003",
  "task_type": "exploit.smb",
  "target_fp": "win2016|smb3|signing:on",
  "hypothesis": "...", "action": "...", "expected": "...", "actual": "...",
  "failure_class": "Env", "outcome": "failed",
  "lesson_ref": "sk-candidate-17" }
```

### 10.4 mission 级资产快照

```
mission 启动 → 冻结 { tools: v12, skills: v40, knowledge: v7, prompts: p8 }
整个 mission 只用这个快照
结束 → 快照版本写入报告
```

三个好处：可复现、可归因（指标变化对应哪次资产更新）、可 A/B。**没有快照，评测全是噪声。**

## 11. 安全与授权

### 11.1 PEP / PDP 分离

```
PEP 执行点（代码，永远在线，不可绕过）
  ├─ 拦截所有副作用
  ├─ 加载策略 → 判定 → 放行 / 拦截 / 挂起
  └─ 记录：动作 + 判定 + 当时生效的策略版本
        ↑
PDP 策略（数据，人来定，可热更新）
  ├─ scope（域名/网段/端口/路径）
  ├─ 风险分级与处置
  ├─ 速率与时间窗
  ├─ 审批规则
  └─ 不可逆动作清单
```

**PEP 是代码且不可绕过，PDP 是数据且随时可改。** 人改策略文件，不改代码，也不给模型下指令。

### 11.2 三条必须留的口子

1. **策略版本化**：每条动作记录当时生效的策略版本。范围中途缩小，日志要能回答"改动之前的请求按当时策略是否合法"。
2. **人工指令是一等事件**（不是停进程改配置）：

```jsonc
HumanDirective =
  | Pause | Resume | Abort
  | ScopeChange { add, remove }
  | Override    { action_id, reason, authority }
  | AddTarget | Reprioritize
```

3. **范围变更触发在途任务重评**：PEP 只拦新动作，管不到已经在跑的进程。策略变更必须发事件，引擎主动取消租约、终止进程、清理在途任务。否则"范围已缩"和"实际还在打"会同时成立——最危险的状态。

### 11.3 安全图

节点：**目标 → 资产 → 发现 → 风险 → 成果**。边有方向语义（`has_asset` / `has_finding` / `implies_risk` / `mitigated_by`）。

价值不在存，在三种查询：

| 查询 | 用途 |
|---|---|
| 影响面 | 这个资产挂了波及哪些成果 → 优先级 |
| 攻击路径 | 从入口到成果的最短链 → 交付物骨架 |
| 覆盖度 | 哪些资产尚未被覆盖 → "下一步打哪" |

**如果 agent 的决策不看图，图就退化成事后画的一张图**——这是安全图谱项目最常见的死法。

细节：**风险 ≠ 发现**。同一发现对不同业务资产严重度不同，`发现 → 风险` 是多对多，中间需要"可利用性 + 业务影响"的判定。

### 11.4 工具集的动态性

```
静态全集 ⊆ mission 授权范围
运行时可用集 = 动态子集
```

**能力可以动态收缩，不能动态扩张。** 否则授权形同虚设。

### 11.5 注入防护

目标回显是**不可信数据**，而模型必须读它。这是 AI 红队场景的核心威胁。

- 回显进 prompt 时放在**结构上隔离的 untrusted 区块**，绝不与指令区混排；
- 凭证/密钥用引用，绝不进 prompt；
- 检测典型注入模式（"忽略之前指令"）→ 告警并标记该证据不可信；
- **来自目标的任何文本不得成为技能内容**（门控硬规则）。

### 11.6 隔离

| 层 | 手段 |
|---|---|
| 执行 | 一次性容器，任务结束即销毁 |
| 网络 | 跳板 / VPN / 出口白名单 |
| 客户 | mission 目录物理隔离，检索强制带 mission 过滤（**代码层，不是提示词**） |
| 密钥 | 加密存储、按需下发、使用留痕 |

**权限系统不是隔离边界。** 真正的边界由容器、网络策略、跳板机强制；网关只负责意图校验与留痕。

## 12. 提示词设计

### 12.1 四段结构

```
┌─────────────────────────────────────────┐
│ [固定] 身份 + 不变量 + 输出 schema        │ ← 逐字节不变，走 prefix cache
├─────────────────────────────────────────┤
│ [稳定] 工具 manifest + 技能注入            │ ← mission 内不变，可缓存
├─────────────────────────────────────────┤
│ [动态] mission 摘要（状态渲染，非历史）     │ ← 每轮重生成
├─────────────────────────────────────────┤
│ [动态] 当前任务 + 线索 + 经验 + 提醒        │ ← Mentor 提醒注入此处
├─────────────────────────────────────────┤
│ [尾部] 本步指令 + Decision 枚举            │
└─────────────────────────────────────────┘
```

前两段必须逐字节稳定，prefix cache 命中率可到 90%+。任何"把时间戳插到开头"的动作都会毁掉缓存。

Token 预算粗分配：固定 40% / 状态 30% / 任务上下文 20% / 指令 10%。

### 12.2 四类 agent 的提示词不能共用

| | Core | Worker | Mentor | JEV |
|---|---|---|---|---|
| 身份 | 任务负责人 | 一次性执行器 | 教练 | 裁决者 |
| 输入 | 完整 mission 状态 | 窄简报 | 漂移指标 + 摘要 | 全量证据 |
| 输出 | Decision | WorkerResult | approve/veto | verdict |
| 自由度 | 高 | 低（工具受限） | 低（只能收紧） | 低（只能裁决） |
| 长度 | 长 | **短** | 中 | 中 |

### 12.3 四条规则

**1. 不变量用结构化清单，不用形容词**

```
✗ "请务必小心，不要超出授权范围"
✓ ALLOWED_SCOPE: ["10.0.0.0/24:80,443", "app.example.com"]
  目标不在清单内 → 返回 status=blocked，不要尝试其他路径
```

**2. 输出 schema 化**：Decision / WorkerResult / verdict 都是枚举 + JSON，自由文本只允许在 `reason` 字段。

**3. Worker 提示词要"窄"**：3 个工具、1 个目标、1 个判据。给 20 个工具它就会乱试。受限任务上，**窄提示词 + 中等模型 > 宽提示词 + 强模型**。

**4. Mentor / JEV 的提示词要"反"**：

```
Mentor: "找出这个决定应该被否决的理由。找不到，才 approve。"
JEV:    "假设这条结论是误报，最可能的原因是什么？排除不了，不要判 confirmed。"
```

举证责任反转，是对抗确认偏误的唯一结构性手段。

### 12.4 current_strategy：别在重建中丢失"为什么"

每轮重建 prompt 只放事实，主控会每天像换了一个人——方向漂移且无法解释。所以状态里必须显式保存策略假设：

```jsonc
"current_strategy": {
  "assumption": "目标存在未授权访问，优先走 IDOR 而非注入",
  "why": "登录后 401→200 的差异最明显，且无 WAF 拦截特征",
  "confidence": 0.6,
  "would_change_if": ["遍历 50 个 ID 都返回 403", "发现统一鉴权中间件"]
}
```

每轮进 prompt；假设不推翻不改写；改写本身是事件。

### 12.5 两个陷阱

- **子智能体不继承父的 system prompt**：它有自己的身份，继承会试图接管全局、汇报无用信息，并破坏缓存。
- **提示词里不放对话历史**：放状态渲染。

## 13. 立项与交付

### 13.1 立项契约

任务级 `success_criteria` 由主控派生，但**判据的源头必须是立项**，否则模型拿自己写的判据给自己打分。

```jsonc
// MissionSpec.acceptance —— 5~8 条可判定验收项
{
  "objective": "评估 10.0.0.0/24 对外暴露面的可利用风险",
  "acceptance": [
    { "id": "a1", "item": "完成存活主机与开放端口清单",
      "evidence": "asset_inventory", "judged_by": "auto" },
    { "id": "a2", "item": "对每个开放服务做版本识别",
      "evidence": "service_version", "judged_by": "auto" },
    { "id": "a3", "item": "对高危服务验证至少一个可利用漏洞（含 POC）",
      "evidence": "exploitable_finding", "judged_by": "jev" },
    { "id": "a4", "item": "绘制从边界到高价值资产的攻击路径",
      "evidence": "attack_path", "judged_by": "human" }
  ]
}
```

整个系统的"靶心"从这里来：任务判据由 acceptance 派生，收口按 acceptance 判定，报告按 acceptance 组织。

### 13.2 报告从黑板生成

```
报告生成器 ← 只读 S2 + S1
          ✗ 不读对话历史
```

好处：可复现（同一状态同一报告）、可增量（跑一半也能出）、可重生成（换模板重跑）。

从对话历史"总结"必丢证据、串事实，且无法验证。

### 13.3 报告结构

```
1. 执行摘要（按 acceptance 逐项：达成 / 部分 / 未达成）
2. 资产与暴露面
3. 发现清单（按严重度，每条带 evidence_ref + 复现命令 + 反证条件）
4. 攻击路径（图 + 文字）
5. 未达成项与原因（失败报告比成功报告值钱）
6. 成本与时间
7. 附录：资产快照版本、策略版本、完整证据哈希清单
```

### 13.4 人审标准

**每个 finding 要让人在 5 分钟内复核完**，必须带：复现命令 + 原始回显 + 判断依据（含 `falsify_if`）。缺一件等于没证据。

v1 可以全自动签发，但**数据结构必须支持签发**——`verdict_by`、`signed_by`、`signed_at` 现在就要有。

## 14. 评测体系

没有评测，所有优化都是盲改。

| 项 | 内容 |
|---|---|
| 靶集 | Vulhub 10 + HTB 5 + 自建 5，每个带 ground truth（位置 + 可利用性 + POC） |
| 基线 | **同模型 plain ReAct 单 agent，同预算、同工具** |
| 指标 | 误报率、漏报率、首次有效线索步数、成本/漏洞、人工介入次数 |
| 回归 | 重放录制的 log，不重新打靶 |
| 归因 | 失败分类统计（Env/Tool/Model/Plan/AuthZ/Deception） |

**没有基线的提升不算提升。** 同模型 plain agent 是很强的基线——很多架构的收益会被它吃掉。

**一次改动的验收**：资产快照 + 提示词版本固定，跑同一套靶，指标显著优于快照前。

## 15. 预算与成本

### 15.1 分层预算

```
mission_budget（token / 时间 / 命令数 / 费用 / 风险额度）
  ├─ 反思预留 ≤ 10%（Mentor + JEV）
  ├─ 收口预留 ≥ 5%（报告与复现必须有钱做）
  └─ 执行池 → 按 ready 任务价值分配
        └─ task_budget
              └─ attempt_budget
```

- 任务超 80% 预警、100% 硬停；
- Worker 可申请追加，主控按剩余池与优先级批准；
- **重启不续命**（§6.5）；
- 风险额度是独立维度：低危便宜、高危贵，天然抑制"随手关服务"。

### 15.2 成本归因

每次模型调用归属到 `(mission, task, 架构动作 ∈ {plan, execute, recover, review, adjudicate})`。

没有归因，几天任务跑完只有一个总数，无法回答"重规划花了多少钱"。

### 15.3 成本模型（交付前必须算）

```
单目标成本 = 主控 token + worker token + 工具耗时折价 + 人工复核时长
单次项目成本 / 发现数  vs  人工同等工作的成本
```

这个数决定商业模式是否成立，不是技术优化问题。

## 16. 模型层与降级

| 模块 | 内容 |
|---|---|
| Router | `task_type × 难度 × 剩余预算 → 模型`；主控强、支线快 |
| Invoker | 超时、重试、降级、流式 |
| StructuredDecoder | JSON Schema 强约束 + 解析失败自动修复重试 |
| PromptCache | 固定前缀跨天命中率极高，是几天任务省钱的关键 |
| CostMeter | 成本归因 |

**降级设计（几天任务必遇）**：

1. 主控必须配**异厂商 fallback**；
2. 模型切换是**显式事件**，标记该段轨迹"跨模型"；
3. 切换后必须**重校**（同一 prompt 下行为差异大，不重校会从谨慎突变激进）；
4. 预期 prefix cache 失效，成本跳一下。

## 17. 反模式清单

1. "发现一个漏洞派一个 agent" —— 漏洞是产出不是输入，派发单元是任务。
2. 主控纯 ReAct 或纯调度器 —— 前者不可审计，后者无法复核子结论。
3. 一次性展开完整计划 —— 必然过时，且强迫模型臆造。
4. 子智能体常驻 —— 上下文腐化、行为漂移、预算难核算。
5. Agent 间点对点聊天 —— 上下文爆炸、不可追溯、写冲突无仲裁。
6. Reflexion 写成"再试一次" —— 没有战术差异就是烧钱。
7. 反思结论直接写技能 —— 单点误判污染全局。
8. 并行不看干扰 —— 打草惊蛇、账户锁死、会话互踢。
9. 把子智能体报告当事实 —— 结论必须挂 evidence_ref。
10. 子智能体直连 shell 绕过网关 —— 授权模型当场失效。
11. 没有终止条件的"长任务" —— 平台期不收口，烧到预算为止。
12. 父子传全文不传简报 —— 3 个 worker 没事，8 个时全线退化。
13. 教练每步都评审 —— 成本从 2.7% 涨到 27%。
14. 用对话历史生成报告 —— 必丢证据。
15. 证据由执行者筛选提交 —— 裁决变成盖章。
16. 上专用图数据库 —— 几万节点用递归 CTE 就够。

## 18. 落地路线

**原则：先纵向切片，再横向加宽。** 按层推进会把"第一次被现实打脸"推到第五周。

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M0 牙签** | 1 个靶 → 1 条链路 → 1 条正确 finding + 带证据的报告。五层都打通，但每层最薄 | 端到端跑通；`kill -9` 后能续 |
| **M1 裁决** | JEV + 全量证据 + 溯源校验 + `falsify_if` | 误报率显著下降；编造证据被拦 |
| **M2 评测** | 靶集 + 基线 + 回归 | 指标优于 plain agent 基线 |
| **M3 并行** | 多目标扇出、租约、干扰粗规则 | 8 并发无重复动作、无越界 |
| **M4 持久** | 事件溯源完整、快照、恢复 | 跨天任务可续；**第 200 步 prompt 与第 20 步同量级** |
| **M5 教练** | I1~I5 梯度、计划评审、漂移检测 | 漂移能在失败前被拦住 |

**数据结构按"几天"设计，验证按"几小时"做。** 事件溯源 M0 就要有，但不需要 M0 证明能跑三天。

## 附录 A：决策记录

| 议题 | 结论 | 被否方案 | 理由 |
|---|---|---|---|
| 主控范式 | 可重入 Plan-and-Execute + ReAct 重规划 | 纯 ReAct / 纯 Plan | 前者不可并行审计，后者必然过时 |
| 主控与 worker | 同一 runtime | 调度器 + 执行器 | 主控必须能亲自复核子结论 |
| 角色 | 装配产物（preset 是可选的糖） | 角色库 | 角色会爆炸 |
| 场景区分 | MissionSpec 扁平字段 + 任务类型注解 | profile 体系 | 一个 mission 内部本来就异构，全局 profile 粒度不对 |
| 边界控制 | PEP 代码 + PDP 数据，AI 判断但不放行 | 全交给模型 | 可逆性判据：错了能撤才交给模型 |
| 失败判定 | 自报 × 判据矩阵 | 自报状态 | 最常见失败是"done 但没做成" |
| 重试 | 四类分开 | "最多重试 3 次" | 混淆不该重试与不该放弃 |
| 教练权力 | 只能否决、带替代、单向收紧 | 可发起动作 | 会变成第二大脑 |
| 教练介入 | 五级梯度，默认静默 | 关口否决 / 每步评审 | 前者太晚，后者太贵 |
| 结论裁决 | JEV，反证优先 | 不做裁决 | 误报是交付的致命伤 |
| 记忆 | 视图 + 事件账本 | 一个大向量库 | 检索方式天然不同 |
| 攻击图 | SQLite 递归 CTE | Neo4j | 过早优化 |
| 并行 | 按需，可计算判据 | 固定并发池 | 协调成本与干扰 |
| 竞争模式 | v1 不做 | 双 worker 竞速 | 成本翻倍，收益不确定 |
